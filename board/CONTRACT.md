# Board contract (protocol v1)

Provider dispatch extension (migration034): `dispatch`, `retry` and
`take_over_with_claude` accept closed `ai` values `claude`/`codex`, deriving
the corresponding backend. Omitted provider preserves older callers;
Codex requires explicit `budget_usd:null` because it has no native dollar
or turn cap. The legacy `default_max_turns` setting applies to Claude Code.
Uncapped teammate work requires the runner owner or a team admin.
`budget_mode` distinguishes explicit no cap from an omitted legacy default.
A finite cap is card-wide; each offer receives only the remaining spend.
Caps range from $0.50 to $1,000, with a configured board maximum for members.
After spend, only the dispatcher, runner owner or admin can raise/clear it.
An exhausted card does not re-offer work; device limits cannot be cleared
by raising a card cap. `run.budget` records the stopped cap and its scope.

Runner `hello`/`advertise` can include up to eight unique closed providers,
bounded labels/versions, `installed`, `signedIn`, `startable` and budget/
resume capabilities. Absent capability data preserves legacy Claude
runners; an explicit empty list advertises no execution provider. Offers
and claims both require current compatible capabilities and fresh device
authority. Paid dispatch retries use their durable choice-bound records,
with live credentials/membership checked after the body and board queue.
The overlap preview exposes online readiness for the selected board repo,
never CLI paths or authentication files. Board views identify the chosen AI.

Local Codex desktop chats connect through Plexiform Settings → Native board
connections → Codex desktop app and CLI → selected team/boards/access →
Connect boards. Open a new Codex chat and use `/mcp` to inspect
`plexiform-board`; Codex MCP settings can restart the connection. Keep
Plexiform open and signed in. Selected-board grants are revocable and
account-bound; the external config contains only the local launcher and
private grant-file location. Native collaboration tools do not themselves
launch an agent or approve completed work.

Status: **LAW** for the four Phase 1 builders (hub, runner, web, board-mcp). 2026-09-30.

1. This file and the code in `board/shared/` (pure, tested; `npm run test:shared`).

To change the contract: edit this file **and** `shared/protocol.js` (or the relevant shared module) in the same commit, bump `PROTOCOL_VERSION` if the change is not purely additive (§9), and keep `shared/test/protocol.test.js` green. That test fails if a message type, outbox kind, fact kind, error code, MCP tool, hook event, runner command or transition row id exists in code but is not named in this file.

Priorities, in order: **P1 Trust** (a dead agent never looks alive), **P2 No lost work** (handover is continuous, never written at death), **P3 Low admin** (Claude keeps the board current).

Rules:

- **Imports.** Every package imports shared code by relative path (`../shared/states.js`). The web imports it from the hub at `/shared/*.js` (§5.1). No package imports another non-shared package, with one exception: `runner/` spawns `mcp/server.js` by path.
- **Tests** live in `board/<pkg>/test/*.test.js` and run with `node --test`. `npm test` (in `board/`) runs all of them. Tests use injectable clocks and temp dirs and never touch `~/.claude*`, `~/.codex`, `~/.claude-traffic-light` or the network.
- **Dependencies** (declared in `board/package.json`, installed into `board/node_modules`, never committed): `ws` (hub server + runner client; pure JS, no native addons), `@modelcontextprotocol/sdk` ^1.30 and `zod` ^4 (mcp). Nothing else without amending this file. `shared/` and `web/` stay dependency-free.
- The widget code outside `board/` is untouched. The runner may `createRequire` the widget's `hooks/session-state.js` and `hooks/session-machine.js` (CJS) to write widget session files (§6.10).

## 2. Runtime targets

| Package | Target | Process model |
|---|---|---|
| hub | Node ≥ 22.13 (unflagged `node:sqlite`), Raspberry Pi 5 arm64, no native deps | One process. One async single-writer queue per board: every state change is `step()` + its effects in **one** SQLite transaction. A 1 s reaper on the hub monotonic clock (`performance.now()`). Listens on `BOARD_BIND:BOARD_PORT` (default `127.0.0.1:8787`) behind Cloudflare Tunnel + Access |
| runner | Node ≥ 22.13, macOS first (Linux works), standalone | Detached supervisor (`spawn(node, [runner/cli.js, 'start'], {detached:true}).unref()`; runnable from a shell), or under the desktop app as a `utilityProcess` running `runner/app-entry.js`, config over `parentPort` (D37a). Spawns the member's own `claude` CLI per run. Talks to the hub over one outbound WSS |
| web | Evergreen browsers, plain ES modules + CSS | Static files served by the hub. No bundler, no framework, no npm deps |
| mcp | Node ≥ 22.13, `@modelcontextprotocol/sdk` stdio server | Spawned by the CLI per run (from the run's `--mcp-config`). Proxies every tool call to the runner over a local socket with the per-run token (§7) |

Clocks: the hub judges every timeout on its **own** monotonic clock at receive time. Runners send **ages** (`*_age_ms`), never instants to be compared. Browsers get `age_ms` and add their own `performance.now()` elapsed. Persisted timestamps are hub wall time (ISO UTC) and are only compared with other hub wall times (D11).

## 4. Identity and auth

### 4.1 Members (browsers)

- **Production (`BOARD_AUTH=access`).** Cloudflare Access sits in front of the hub, with any IdP (GitHub, or the one-time PIN email IdP used for the dogfood deploy): the hub reads only the verified `email` claim, never a GitHub identity claim. On every HTTP request and WS upgrade the hub verifies the `Cf-Access-Jwt-Assertion` header: RS256 against `https://<BOARD_ACCESS_TEAM>.cloudflareaccess.com/cdn-cgi/access/certs` (cached, refetched on unknown `kid`), `aud` contains `BOARD_ACCESS_AUD`, `exp` in the future. The verified `email` claim maps to `members.email` (case-insensitive) → the member. No match → `403 FORBIDDEN` ("not a member of this board"). Members are created by an admin with an email; GitHub login/id are optional (an email-only member has `github_login: null` on the wire) (D4). Verification uses `node:crypto` only. `BOARD_AUTH=access` without `BOARD_ACCESS_TEAM` and `BOARD_ACCESS_AUD` refuses to start.
- **One sign-in, several orgs.** An email may be a member of several orgs (one `members` row each). The row that acts is: the org named by header `Board-Org` or query `?org=` (not a member there → `403`); else the only row; else the row in the org of the request's resource (the board, card, permission request, device or member in the path; none there → `404`); else `409 CONFLICT` with `error.orgs:[{id, name, member_id}]`, never a silent pick. The web retries with `?org=` (from its URL) or the first listed org and sends `Board-Org` on every call. Browser sockets take `?org=`; without it the subscribed board's org decides.
- **Removal and expiry.** `DELETE /api/members/:id` (admin) soft-removes a member (`members.removed_at`, migration 005): they no longer authenticate, their devices are revoked (live runner sockets closed `4403`), and their live browser sockets are closed `4403`. Every browser `subscribe` re-reads membership, and the reaper re-checks open sockets each pass. Under Access a browser socket is closed `4401` when the JWT it connected with expires (`exp`); the web then re-authenticates.
- **Local dev (`BOARD_AUTH=dev`).** Allowed **only** when the hub is bound to a loopback address; otherwise it refuses to start. **Dev auth must never sit behind any proxy or tunnel**: the hub refuses `BOARD_AUTH=dev` when `BOARD_PUBLIC_URL` or `BOARD_TUNNEL_PROBE_URL` is set. `POST /api/dev/login {github_login}` needs header `Board-Dev-Secret: <secret>` (`BOARD_DEV_LOGIN_SECRET`, else random per start; printed to stderr at startup as `http://<bind>:<port>/#dev_secret=<secret>`, which the web keeps in `sessionStorage`), is rate limited per IP (§5.2), and sets cookie `board_dev=<member_id>.<hmac>` (HttpOnly, SameSite=Strict, HMAC with the hub secret). `BOARD_DEV_SEED=1` creates org `dev`, board `DEV` (key prefix `DEV`), members `alice`/`bob` (negative github ids) and repo from `BOARD_DEV_REPO` if set.
- **Accounts (`BOARD_AUTH=accounts`, D51–D58).** The hub runs its own sign-in: email one-time codes (sign-up = sign-in), a per-install desktop device token sent as `Authorization: Bearer bdt_…` on every HTTP call and on the `/ws/board` upgrade, or a `__Host-buddy_session` cookie for a plain browser (with CSRF). Users (`users`) and memberships (`members.user_id`) are split (migration 009). Routes, shapes, errors and limits: `ACCOUNTS-API.md`. Member routes resolve the acting member from the user's memberships exactly as "one sign-in, several orgs" below; a user in no team gets `404` there.
- **Embedded (`BOARD_AUTH=local`).** Loopback only; every request carries cookie `board_local` = a per-launch secret the hub reports to the desktop app over `process.parentPort` (D35).
- Browsers never hold a token beyond the Access cookie (or the dev or local cookie). Mutating routes require `Content-Type: application/json` and reject a cross-origin `Origin` header (`403 FORBIDDEN`). Request limits: D105.

### 4.2 Runners (devices)

- **Enrolment.** A member calls `POST /api/devices {name}` and gets `{device_id, device_token}` once. `device_token` = `bdt_` + base64url(32 random bytes); the hub stores `sha256(token)` hex in `devices.token_hash`. The member runs `board-runner enroll --hub <url> --device <id> --token <token> [--cf-client-id … --cf-client-secret …]`, which writes `~/.board/device.json` (0600).
- **Every runner connection** sends `Authorization: Bearer <device_token>`. In production the runner also sends the device's Access service token (`CF-Access-Client-Id`, `CF-Access-Client-Secret`); Access turns that into a `Cf-Access-Jwt-Assertion` whose `common_name` must equal `devices.cf_service_token_id` of the same device. Revoked device (`revoked_at`) → close `4403`.
- **Run tokens.** On a successful claim the hub mints `run_token` = `brt1.<b64url(JSON{c:card_id,r:run_id,f:fence,e:hub_epoch})>.<b64url(HMAC-SHA256(BOARD_SECRET, payload))>`. The runner passes it to board-mcp and the hook shim (env `BOARD_RUN_TOKEN`), checks it on every local IPC call, and attaches it to every `rpc` and outbox message's run. The hub verifies the HMAC, then that `r`/`c` match an **unended** run and `f` is the card's current fence. So a fence bump kills every token of the old run (T4).
- Hub secrets: `BOARD_SECRET` (env, ≥ 32 bytes) or, if absent, generated once and stored in `hub_meta.k='secret'` (D12).

### 5.2 HTTP API

All JSON. Every response carries header `Board-Protocol: 1`. Errors are `{"error":{"code":"<CODE>","message":"…", …extra}}` with the status from `protocol.ERRORS`. Every mutating request carries a client-generated `request_id` (uuid). The hub remembers `(member_id, request_id) → response` for 10 min and replays it (D8). `dispatch`-like actions are additionally idempotent in the DB via `dispatches.request_id`.

Card creation, card editing and comments recheck the current credential owner/epoch, account, membership, team and writer role after reading the body and inside the board queue. Before a cached response, the same checks also require a current writable target. These three operations bind replay to the HTTP method, route, target and canonical JSON payload; changed requests return `CONFLICT`, including reuse between these operations and an unrelated generic-cache route. Cache-eligible requests sharing an actor and request ID are serialized, including concurrent cross-route collisions, so one mutation supplies their cached response. Paid dispatches and routes with their own durable replay handling retain their separate idempotence paths. This is the same 10-minute, in-memory replay window; it is not restart-durable. Credentials and authority are server context and cannot be selected by JSON fields.

**Rate limits** (`hub/ratelimit.js`, token buckets on the hub monotonic clock, `config.rateLimits` overrides): every mutating request is limited per client IP (`mutate_ip` 300/min; `/api/dev/login` uses `login_ip` 10/min instead), and after auth per member (`mutate_member` 120/min), with a tighter per-member bucket for the actions that start paid runs (`dispatch`, `retry`, `take_over_with_claude`: `dispatch_member` 30/min). Two runner RPCs have buckets keyed by the member the run works for (`runs.on_behalf_of`), taken after the run is verified: `board_create_card` (`agent_card_member` 20/h) and `board_add_lesson` (`agent_lesson_member` 30/h; taken before the duplicate lookup, so an exact repeat costs a token too). `GET /api/boards/:board_id/presence` has its own per-member bucket (`presence_member` 60/min). A label rename or a delete with `strip` (each rewrites up to 2,000 cards, D91) also spends `label_rewrite_board` (10/h per board), taken after the 2,000-card check so a refused rewrite costs nothing. An integration acting through `actAs` (D42) never spends `mutate_member`: `integration_conn` (120/min per connection) on every call, plus `integration_card_conn` (20/h per connection) on `createCard`, and `integration_card_subject` (5/h per connection and provider user, keyed on its `refHash`) on a `createCard` inside an `act()` that names `meta.subject` (D42 addendum F8). A webhook whose connector names its provider user (`rateSubject`) also spends `integration_user_cmd` (30/min per connection and that user's `refHash`), and its refusals are audited at most `integration_rate_audit_conn` (6/min per connection) times (D42 addendum C3). Inbound webhooks (D42) are not `/api` mutations: `webhook_fail_ip` (30/min per `<connection id>|<client IP>`; an IPv6 client is keyed on its /64, `failBucketKey`, since it usually holds the whole prefix) is spent when the signature check fails (the answer is then 401, or 429 once the pair is over it) or the body is over 1 MiB (413) or late (408), and **never refuses a delivery whose signature verifies**: a provider's egress IPs also carry anyone's forged posts to a known connection id. Before the body is read only in-flight read caps apply (D42: per pair, per client IP, per connection; over one → 503 `Retry-After: 1`, body unread), never a failure count; `webhook_conn` (600/min per connection) is spent only by a delivery whose signature verified and that is not a duplicate, so whoever merely knows a connection id, or replays a finished delivery, cannot drain it. A replayed `request_id` served from the D8 cache costs nothing. Over the limit: `429 RATE_LIMITED`, header `Retry-After: <s>`, body `error.retry_after_s`. The client IP is the socket address, or `CF-Connecting-IP` under `BOARD_AUTH=access` (the hub sits on loopback behind the tunnel). Buckets live in hub memory and reset when the hub restarts; an idle bucket is dropped only after max(10 min, its rule's period), so an hourly bucket cannot be emptied, waited out for 10 minutes and come back full.

### 5.3 WebSocket `/ws/board`

Read-only push; every mutation goes over HTTP. Frames are JSON text. Server pings every 20 s (WS ping frame); client may send `ping` → `pong`. A browser socket may send 60 frames per 10 s (`ws_browser`); past that each frame gets `error{code:'RATE_LIMITED'}` and is ignored.

Client → hub (`browser→hub` in `protocol.SHAPES`):

- `hello {protocol}` — first frame. Incompatible → `error{code:'PROTOCOL_UNSUPPORTED'}` then close `4426`.
- `subscribe {board_id}` → hub replies `snapshot`, then streams patches for that board. One board per socket in Phase 1 (a second `subscribe` replaces the first). Membership is re-checked on every `subscribe`; a removed member's socket is closed `4403`.
- `unsubscribe` `{board_id}`, `ping {}`.

Hub → client (`hub→browser`):

- `welcome {protocol, hub_epoch, member, user?}`. In accounts mode `member` is `null` until a subscribe picks one, and `user {id, display_name}` is added.
- `session.revoked {}` (accounts): the device token or cookie session this socket was opened with was revoked (sign-out, device revoke, account deletion); the socket then closes `4401`.
- `snapshot {board_id, board:{id,name,key_prefix,archived_at,settings,labels:[LabelDef]}, cards:CardView[], members:[{member_id,name,login,avatar_url}]}`. `cards` leaves archived cards out (D94).
- `card.upsert {board_id, card:CardView}` — full replacement of one card's view, sent on any change to it; never for an archived card (restoring one sends it).
- `card.remove` `{board_id, card_id}` — the card left the board: archived (D94).
- `board.labels` `{board_id, labels:[LabelDef]}` — the board's whole label registry after any change to it (D91). `LabelDef = {id, name, color, description}`; `color` ∈ `protocol.LABEL_COLORS` (`grey`, `red`, `orange`, `yellow`, `green`, `teal`, `blue`, `purple`, `pink`, `brown`).
- `lease.tick` `{card_id, live:LeaseView, state_age_ms}` — at most 1/s/card (`TICK_MAX_RATE_MS`), only for cards in `ACTIVE`, only when something changed or every 5 s.
- `event.append {card_id, event:FeedEvent}`.
- `team.presence {members:[{member_id, name, sessions:[{agent, repo_short, branch?, state, since, summary?}]}]}` — the board's team presence (D37b): sent right after every `snapshot`, then whenever the view changes. Only members of the board's org, only sessions in repos linked to **this** board.
- `pong {}`, `error {code, message}`.

`team.boards` `{org_id, boards:[{id,name,key_prefix,archived_at}]}` carries the team's complete board list, including archives, after create, rename, archive or restore. Only live members of that org receive it; membership is rechecked before sending.

When the socket drops, the web shows one banner "Board connection lost: states as of HH:MM:SS" and renders every card with `cardFace(view, {connection_lost:true})`. It never marks cards unresponsive itself. On reconnect it re-subscribes and replaces everything with the new `snapshot`. A changed `hub_epoch` needs nothing special.

## 6. Runner ↔ hub

### 6.1 Connection

`wss://<hub>/ws/runner` with the §4.2 headers. Reconnect with `liveness.reconnectDelay(attempt)` (exponential, full jitter, **cap 30 s**). A second connection from the same device replaces the first (old one closed `4409`). A device may send 3000 frames per 10 s (`ws_runner`); past that the hub closes the socket `4429` and the runner reconnects with backoff and replays its outbox (nothing is lost).

1. Runner → `hello {protocol, device_id, runner_version, outbox_head_seq, runs:[{run_id, card_id, fence, local_state}], form_factor?}` where `local_state` ∈ `running | paused_offline | fenced | ending` and `form_factor` ∈ `laptop | desktop` (battery present; `policy.json` `form_factor` overrides). The hub stores it in `devices.form_factor` (migration 002).
   `outbox_id` (a UUID the runner creates together with its outbox, stored in `head.json`) and `outbox_acked_seq` (the runner's persisted acked seq) settle the outbox before `welcome` (migration 004): a changed `outbox_id` means the outbox was wiped and restarted at seq 1, so the hub resets `devices.last_seq_acked` to 0 (and moves `devices.seq_base` past every stored `events.seq` of the device, keeping `UNIQUE(device_id, seq)`); then `last_seq_acked = max(hub, outbox_acked_seq)`, so a hub restored from an older backup never waits for entries the runner already dropped. Each move is a `device.outbox` journal row (§15).
2. Hub → `welcome {protocol, hub_epoch, device_id, member_id, last_seq_acked, allowlist:[{repo_id, canonical_url, aliases}]}`. `allowlist` = every repo on any board the device's member belongs to (the input to `scope.matchRepo`, D14).
3. Runner replays every outbox entry with `seq > last_seq_acked`, in order, as `out` frames (with `delayed:true`), then sends `advertise`, then its first `hb` immediately (not waiting for the 15 s tick).
4. Hub re-sends pending `offer`s for this device and any `cmd` still implied by card state (e.g. `stop` for a run whose card is failed/handed_over, `handover_begin` for a current run whose card is `handing_over`, so a hub restart never loses it). Commands queued for an offline device are bounded (30 min, 50 per device); older ones are re-derived this way. The runner dedupes `cmd_id` over its last 1000.

### 6.4 Claim

1. Offer arrives. The runner checks its **local** `policy.json` (authoritative): repo opted in; dispatcher is the owner, or in `accept_from[repo_id]` (auto-accept), else ask the owner via Buddy (local confirm, T1); concurrency < `max_concurrent`; no `never_auto` label.
2. `claim {id, card_id, request_id, expected_fence}`. The hub runs `step(card, {type:'claim', expected_fence}, ctx)` (#`3`: CAS on `run_state='queued' AND fence=expected`, fence+1, `runs` row, lease). Result → `claim.result`.
3. On `ok`: fetch base ref, create worktree `~/.board/worktrees/<repo_id>/<KEY>-r<fence>` on branch `branchName(KEY, fence)` (from `seed.from_snapshot` when present: fetch `refs/board/<KEY>/*` explicitly, spike 7), write run dir, spawn the CLI (§7.1). The runner itself enforces `T_CLAIM_MS`: no `system/init` + first activity within 120 s → `prep.failed` (#`5`).

### 6.5 Outbox

- Append-only NDJSON log at `~/.board/outbox/<device_id>.ndjson` plus `acked.json` (`{seq}`), written with `writeJsonAtomic`-style rename. `seq` is per device, starts at 1, strictly increasing, never reused (persist the head before sending).
- Every hub-bound message about a run is **constructed from scoped data and serialized only by `scope.serializeOutbound(msg, scope, {requireRepoId:true})`**. The outbox never holds bytes that did not pass it (exit f).
- `delayed:true` when the entry was created while disconnected, by an earlier supervisor process, or is replayed more than `HB_MS` after it was written. A replay of an entry a few seconds old (a dropped socket) is not delayed. Delayed `activity` never moves a card (rows `n-activity-delayed`, D3).
- The hub dedupes by `UNIQUE(device_id, seq)` in `events` (stored as `devices.seq_base + seq`), applies in seq order, and acks cumulatively. A gap before the **first** `out` frame of a connection can never fill (the runner replays contiguously from its oldest unacked entry): the hub skips it (fast-forwards `last_seq_acked`, journal `device.outbox {reason:'gap'}`) instead of buffering forever. A stale-fence outbox entry is **acked and dropped** (the first per run is recorded as a `salvage` note event, later ones as internal `outbox_dropped` rows), never retried forever.

### 6.7 Commands and the stop recipe (spikes 1c, 5b–5e)

| `cmd` | Runner does |
|---|---|
| `interrupt` | stdin `{"type":"control_request","request_id":"<id>","request":{"subtype":"interrupt"}}`; SIGINT if no `control_response` in 2 s |
| `stop` | **Stop recipe**: interrupt → wait ≤ `INTERRUPT_WAIT_MS` (5 s) → end stdin → SIGTERM → after `STOP_GRACE_MS` (10 s), if the CLI pid **and** its start time (`lstart`) still match: SIGKILL it and `kill -9 -- -<pgid>` every descendant process group (Bash tool trees have their own pgid and reparent to 1). Then snapshot, final facts, exit the run |
| `park` | Stop recipe after asking for a final handover (as `handover_begin` with `wait_ms` 30 s); the hub already bumped the fence, so the final writes go as `salvage` (§6.9, D7). A `FENCED` hb.ack / `fenced` frame inside that window is expected and does not cut it short |
| `handover_begin` | Inject "write your final handover now via board_write_handover" at the next tool boundary (PostToolUse `additionalContext`, or a stdin user message if idle), wait ≤ `wait_ms` (90 s) for `board_write_handover`, then stop recipe, snapshot + push, `handover.complete` |

**Terminal state comes from the stream's `result` message** (`subtype`, `total_cost_usd`, `num_turns`, `terminal_reason`, `permission_denials`), never from the Stop hook (Stop does not fire on `error_max_budget_usd`, spike 3). Mapping: `success` after `board_complete` → nothing (hub already moved); `error_max_budget_usd` → `run.failed{budget}`; rate-limit / usage-limit → `run.failed{limit}` (3 backoff retries first for transient 429s); network patterns → `network` (reuse `failureOf()` regexes from `hooks/set-status.js`); anything else, or CLI exit without `result` → `error`. `--max-budget-usd` overshoots by one API call: the budget is soft by one call (spike 8 in "Design changes forced").

### 6.8 Scope and gate (runner obligations)

- `scope.scopeOf({cwd, toplevel, remote_url}, {allowlist, opted_in})` runs before anything about a session is built. `null` → nothing is built (exit f). `allowlist` entries may be canonical (`github.com/o/r`, what the hub stores and sends in `welcome`) or remote URLs; `matchRepo` normalises both. Only allowlist names get this leniency: a session's `remote_url` must be a real network remote.
- **Identity input (D27):** `remote_url` = `git config --get remote.origin.url` (the URL the member configured), not `git remote get-url origin` (which expands `url.<base>.insteadOf`). insteadOf is a local transport rewrite (SSH↔HTTPS, a mirror, a local bare repo in tests); the repo's identity is the name the member gave it. Both are fail-safe: a rewrite to a different host can only make a session *not* match.
- Every path in a fact goes through `filterPath(p, toplevel)`; `null` → the path is dropped. Every free text goes through `redact(text, toplevel)`.
- Gate G is `liveness.gate({ack_age_ms: ackAge(...), fenced, wake})` evaluated on the runner's clocks, where the ack is the last `hb.ack` with `current:true` for that run. Sleep is detected with the tick-gap detector (`sleptEstimate`, 1 s tick) plus Buddy's powerMonitor relay (spike 8: `hrtime` includes sleep on macOS, so Δwall − Δmono is useless). Closing the gate = PreToolUse denies everything + `interrupt` (SIGKILL after 10 s) + local snapshot + `local_state:'paused_offline'`. A 530/1033 from the edge ("origin down") never reopens a closed gate. Only a `current:true` ack does.

### 6.9 Zombie revival and salvage

A run that called `board_complete` or `board_release` **ends normally** on `hb.ack current:false` / `fenced` / `RUN_ENDED`: tools are denied with "this run has ended" (never "taken over"), the turn finishes, and the final facts + snapshot stay on the **outbox** (rows `31` and `25` keep the fence); only a requeueing release (row `24`, fence bumped) sends its final snapshot as `salvage`, without a fenced note.

Otherwise `hb.ack current:false` (or `fenced`, or an `rpc` answered `FENCED`/`RUN_ENDED`): set `fenced` (PreToolUse denies "this card was taken over"), interrupt then stop recipe, snapshot to `salvageRef(KEY, n)` (push if possible), send `salvage` frames (handover narrative, snapshot ref, note), tell Buddy. **Promotion rule (D7):** the hub records salvage as events; when a salvage `handover`/`snapshot` comes from the card's **most recent** run and no newer run has been claimed, the hub also promotes it to the current handover version / snapshot with provenance `post_fence`. This is how `park`, `stop` and timed-out handovers keep their final narrative.

### 6.10 Local surfaces (runner-internal, for Buddy later)

`~/.board/` (`BOARD_HOME`), dir 0700: `device.json` (0600), `policy.json` (0600, runner-local, authoritative, never synced: `{repos:{repo_id:{opt_in, local_path, allowed_domains, allow_write_extra, bash_allow, max_concurrent, budget_per_run, budget_per_day, share_level, approvals_from}}, accept_from:{repo_id:[member_id]}, backends:{claude:'/path/to/claude'}, never_auto_labels}`), `outbox/`, `ledger.json` (runs: `run_id, card_id, fence, pid, lstart, pgid, worktree, session_id, run_dir`), `run/<run_id>/` (0700: `settings.json`, `mcp.json`, `ipc.sock`), `worktrees/`. Control socket `~/.board/runner.sock` (NDJSON, 0600) for Buddy: `status`, `opt_in`, `confirm_offer {request_id, accept}`, `stop_all` (works with the hub down), `host_suspending`, `host_resumed`.

When a run ends, the runner deletes its run dir and removes its worktree (`git worktree remove --force` + `prune`); the branch and the snapshot/salvage refs stay in the member's repo. A worktree whose last snapshot was never pushed is kept (logged) for a manual salvage. A run that ended while its prep was still awaiting (T_claim hit during a slow fetch) never spawns the CLI and never re-enters the ledger.

On supervisor restart: every ledger run whose pid + lstart still match is an orphan → stop recipe → snapshot → `run.failed{error, reason:'supervisor crash'}` (#`22` from any active state incl. unresponsive/orphaned).

Widget session files: the runner writes one session file per run through the widget's own `hooks/session-state.js` into `$CLAUDE_TRAFFIC_LIGHT_HOME/sessions` (default `~/.claude-traffic-light/sessions`), tagged with the card key, so Phase 1 needs no widget change. Tests set `CLAUDE_TRAFFIC_LIGHT_HOME` to a temp dir.

### 7.2 Local IPC (runner ⇄ board-mcp and hook shim)

- Transport: Unix domain socket `<run_dir>/ipc.sock` (run dir 0700, socket 0600). Windows (later): named pipe `\\.\pipe\board-<run_id>-<random>`. One socket per run.
- Framing: NDJSON, one JSON object per line, UTF-8, max 1 MiB per line.
- Every request carries `id` (string, unique per connection) and `token` (= `BOARD_RUN_TOKEN`). The runner compares the token with the run's token in constant time; mismatch → `{ok:false, error:{code:'BAD_RUN_TOKEN'}}` and the connection is closed.
- Requests (`ipc→runner` in `protocol.SHAPES`):
  - `hello {id, token}` → `{id, ok:true, result:{run_id, card_id, key, fence, repo_id, tools:[…MCP_TOOLS]}}`.
  - `tool` `{id, token, name, args}` → `{id, ok, result|error}`. `name` ∈ `MCP_TOOLS`.
  - `hook` `{id, token, event, payload}` → `{id, ok, result:{stdout:object, exit_code}}`. `event` ∈ `HOOK_EVENTS`; `payload` is the CLI's hook stdin JSON.
  - `cancel` `{id, token, re}` → `{id, ok:true, result:{}}`. board-mcp sends it when the CLI cancels a call it is holding (`re` = that call's request id). For a held `approval` the runner answers the held call with deny and sends rpc `approval_cancel` so the request is withdrawn on the hub.
- Responses: `{id, ok:true, result}` or `{id, ok:false, error:{code, message}}` with codes from `protocol.ERRORS` (`GATE_CLOSED`, `HUB_UNREACHABLE`, `OUT_OF_SCOPE`, `FENCED`, `VALIDATION`, …).

### 7.3 board-mcp tool surface (Phase 1)

Server name `board`, stdio, one per run. Each tool forwards `tool {name, args}` over IPC and returns `result` as a single JSON text content block; an IPC `error` becomes an MCP tool error (`isError:true`) whose text is `"<code>: <message>"`. Read-only tools carry `annotations.readOnlyHint: true`. No other tools exist: no heartbeat, move, assign, claim, dispatch, done, policy, budget, credentials or other repos' cards (§10, D33). The only card an agent can create is a To do child of its own card (D31).

**Scopes** (`protocol.TOOL_SCOPES` / `MCP_TOOL_SCOPES`; every tool has exactly one, `mcp/tools.js` refuses to load otherwise). All of them sit inside the run's repo scope: the runner exists only for an opted-in repo (`scope.scopeOf` default-denies everything else) and the hub verifies run token, fence, unended run and `repo_id` = the run's repo before any method runs (§6.6).

| Scope | Allows | Tools |
|---|---|---|
| `card:read` | this run's card, its parent and its children | `board_get_card` |
| `repo:read` | titles, overlaps and notes of this board's cards in this run's repo | `board_list_cards`, `board_check_overlap`, `board_recall` |
| `card:write` | writes to this run's own card only | `board_update_status`, `board_append_progress`, `board_write_handover`, `board_ask_human`, `board_comment`, `board_attach_evidence`, `board_complete`, `board_release`, `board_declare_plan` |
| `card:create_child` | a new To do child of this run's card, same board and repo | `board_create_card` |
| `lesson:suggest` | append a lesson suggestion for this run's repo in the board's org; never read back to agents | `board_add_lesson` |
| `permission:ask` | ask this card's approvers; cannot grant | `approval` |

The hub keeps the same map for runner RPCs (`hub/rpc.js` `METHOD_SCOPES`), runner-only plumbing included (`team_context`: `repo:read`, `approval_cancel`: `permission:ask`); `handleRpc` refuses (`FORBIDDEN`) any method without an entry. Scopes are enforced by what each method reads and writes, not by claims in the run token. `board_recall` reads only handoff notes whose card is on the run's board.

### 7.4 Hook shim (`runner/hook-shim.js <event>`)

- Reads the hook JSON from stdin and forwards `hook {event, payload}` over IPC. Prints `result.stdout` (JSON) and exits with `result.exit_code`.
- **Dead-man check first** (spike change 2): if `BOARD_SUPERVISOR_PID` is not alive or its start time ≠ `BOARD_SUPERVISOR_LSTART`, or the socket is unreachable, or IPC fails/times out: for `pre` print `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"board supervisor unavailable"}}` and exit 0 (exit 2 with the reason on stderr if even that fails). Every other event exits 0 silently. **Fail-closed for `pre`, fail-quiet for the rest.**

What the runner answers per event (the facts go to the outbox, §6.5):

| `event` | CLI hook | Runner does | stdout |
|---|---|---|---|
| `start` | SessionStart (`startup`, `compact`, `resume`) | mark "not degraded"; `startup` on a seeded run → seed (handover + card + "you are run rN; rN-1 ended …") + team context; `compact` → re-inject the current handover | `{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"…"}}` |
| `prompt` | UserPromptSubmit | team-context block (≤ budget) | `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":"…"}}` |
| `pre` | PreToolUse | gate G (wait ≤ `wait_ms` on `await_ack`), fenced check, path confinement of Read/Glob/Grep/Edit/Write/NotebookEdit to the worktree after realpath, deny `git push` to anything but `origin board/<KEY>-r<n>`; record `tool_in_flight` (+ Bash timeout) | deny object, or `{}` to proceed |
| `post` | PostToolUse | facts (`tool_end`, `file`, `command`, `git`, `plan` from TaskCreate/TaskUpdate/TodoWrite); pending trusted comments; one-time overlap delta; narrative nudge when > 10 min or > 25 calls old; handover_begin injection; code snapshot at a quiescent point | `{"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":"…"}}` or `{}` |
| `postfail` | PostToolUseFailure | `error` fact | same shape as `post` |
| `precompact` | PreCompact | snapshot; `compacted` fact | `{}` |
| `stop` | Stop | if the agent is stopping without `board_complete`/`board_ask_human`/`board_release`: remind it (not a terminal signal) | `{"hookSpecificOutput":{"hookEventName":"Stop","additionalContext":"…"}}` or `{}` |
| `stopfail` | StopFailure | `error` fact only (terminal state comes from `result`, §6.7) | `{}` |
| `substop` | SubagentStop | `subagent` fact (500 chars) | `{}` |

A missing `start` within `DEGRADED_NO_SESSIONSTART_MS` (30 s) of spawn → `degraded` fact; the gate then relies on supervisor signals (design §6).

**Answer delivery** (design §3.7): mid-turn at the next tool boundary via `post` `additionalContext`; when the agent is idle or blocked, as a stdin user message. The runner reports `comment.delivered` with `via`.

**Untrusted text is enveloped** (`untrusted(source, text, nonce)` in `shared/untrusted.js`, D30): every piece of text people or earlier runs wrote that the runner puts in the agent's context (the first prompt's card title, the seed handover/answer/review/comments at `start`, the re-injected handover at `compact`, team context at `start`/`prompt`, overlap deltas, delivered comments and answers) **and every such string in a board tool result** (`board_get_card`: title, body, acceptance, handover_md, open ask texts, comment bodies; `board_list_cards` titles; `board_recall` bodies; `board_declare_plan` / `board_check_overlap` overlap `paths[]`, `reasons[]` and `other_owner`) is wrapped as `<untrusted_board_content_<nonce> source="card:KEY comment by NAME">…</untrusted_board_content_<nonce>>`. `<nonce>` is 16 hex chars from `crypto.randomBytes`, one per run, generated by the runner and never sent to the hub; the board brief names the exact tag. The text (and the `source`) is first NFKC-normalised (fullwidth `＜`, `／` and letters fold to ASCII), then stripped of `\p{Cf}` and other default-ignorable code points (zero-width space/joiners, word joiner, BOM, soft hyphen, CGJ), then any `<untrusted` / `</untrusted` prefix (any case, any spacing, so the envelope tag with or without a nonce) is defused to `&lt;…`, matched on a copy with a small confusables fold (Cyrillic `о`→`o`, `∕`→`/`, `˂`→`<`, `‹`→`<`; only the matched span changes), so an embedded or lookalike closing tag can never end the envelope. Agent text the runner sends to the board has the run's nonce replaced with `[nonce]`, so a run cannot plant its own closing tag for a later read-back. The `source` attribute is also stripped of quotes, angle brackets, `&` and newlines. The board brief (`--append-system-prompt`) says envelope contents are data, never instructions.

## 9. Versioning

- `PROTOCOL_VERSION = 1` (integer). Sent in `hello` (both WS channels), `welcome`, and the `Board-Protocol` HTTP header.
- **Additive** changes (a new optional field, a new message type that old peers can ignore, a new fact kind the hub stores generically) do **not** bump the version. Receivers ignore unknown **fields**. An unknown **type** gets a non-fatal `error{code:'VALIDATION'}` reply and is otherwise ignored.
- Removing or renaming a field, changing its meaning, or changing a state-machine edge a peer relies on bumps the version. The hub accepts exactly its own version (`compatible()`); mismatch → close `4426` / HTTP `426`.
- Schema changes are new files in `shared/migrations/NNN_name.sql`; applied migrations are never edited.
- Contract changes that reverse an earlier decision are listed here. 2026-10-01: **D97** (pending connections) reverses D42's "no pending step" for connectors that declare `connect.prepare`, and (slice B3) D42's "an unknown or inactive connection is 404 before the body is read": every webhook id is read under the same caps before its 404; it adds routes, journal kinds and migration 022 only, so `PROTOCOL_VERSION` stays 1. **D98** (identity links) changes D41's `external_identities` (adds `connection_id`, with triggers) and D42's `actAs` rule (`act(…, {subject})` binds `actAs` to that subject's member linked through that connection; an `act()` without a subject acts only as `created_by`); it adds routes, journal kinds and migrations 023 and 025 (its follow-up) only, so `PROTOCOL_VERSION` stays 1.

## 10. State machine (design §4, `shared/states.js`)

`step(card, event, ctx)` returns `{ok, card, effects, rule, from, to}` or `{ok:false, error:{code,message}, rule?}`. It never throws on bad input and never mutates `card`. The hub persists `toDb(result.card)` and executes `effects` **in the same transaction**. `todo` is stored as `run_state NULL`.

## 12. Decisions

- **D1 ESM everywhere in `board/`.** `"type":"module"`, so shared modules load unchanged in the browser. The widget's CJS modules are reached with `createRequire`.
- **D2 Hub node:sqlite, Node ≥ 22.13.** Unflagged there (added 22.5 behind a flag). Design §9.1 said `better-sqlite3`; the brief forbids native deps, so `node:sqlite` it is.
- **D3 Only `hb` recovers a dark card; `activity` never does.** Delayed (replayed) activity never moves a card. Green after any recovery needs fresh, non-delayed activity (Power Nap guard, exit c).
- **D4 Member identity = verified Access email → `members.email`.** Members are pre-registered by an admin by email (GitHub login + id optional; the dogfood deploy uses the Access one-time PIN IdP). The GitHub id isn't read from Access claims in Phase 1: the claim shape is unverified (S3). Revisit after S3.
- **D5 Double boot keeps `pre_reconnect_state`; `handing_over` rides through a boot** with its 3-min timer restarted (rows `19r`, `19h`).
- **D6 Answers while dark are stored, not refused** (row `9d`). resume_to drops to `quiet` when nothing is left open, so a recovered card doesn't show a stale "Needs you".
- **D7 Park, stop and timed-out handovers bump the fence immediately** (§5.3 law: every stop/park/takeover bumps). The run's final narrative and snapshot come in through the **salvage lane**, and are promoted to current when they come from the card's most recent run (§6.9). **D7b** `complete` is allowed from `quiet` as well as `running` (the MCP call is itself activity).
- **D8 Idempotency.** Every mutating HTTP call and every claim carries a `request_id`. Dispatch-like actions are idempotent in the DB (`dispatches.request_id`); other actions via a 10-min `(member, request_id)` response cache.
- **D9 Handover `done` prepends, other sections replace** (newest first, 50 entries). `plan` may be markdown or `[{text,status}]`; the newer of the narrative plan and the TodoWrite mirror wins.
- **D10 Fence token = `{n, epoch}`; only `n` decides.** Epoch tells the runner a hub restart happened. The DB stores the integer; restore = +1000 and a new epoch (`applyRestoreBump`).
- **D11 Long timers use persisted hub wall time** (`cards.state_since`, same machine). HB TTL and orphan silence use in-memory hub monotonic time, and restart with the process (covered by boot grace).
- **D12 One hub secret** (env `BOARD_SECRET` or generated into `hub_meta`) signs run tokens and dev cookies.
- **D13 Green is computed twice:** by the hub at send time and by the web from aged values each second. It shows only if both agree (`cardFace` uses the aged values; `LeaseView.green` is the hub's value).
- **D14 A runner advertises only repos that are both opted in locally and on a board allowlist.** The allowlist comes in `welcome.allowlist` and is refreshed by a new `welcome`-shaped push only on reconnect in Phase 1 (admins adding a repo take effect on the runner's next connect).
- **D15 CLI env is an allowlist** plus the isolation variables (§7.1). This neutralises shell-snapshot Gap A and keeps unrelated secrets in the member's env off the run.
- **D16 Interrupt is the stream-json `control_request` (spike 1c), SIGINT only as a fallback.** Stop follows the spike's SIGTERM-tree recipe.
- **D17 One device-level HB carries all runs.** The hub answers `hb.ack` per run; `current:true` is the only thing that reopens gate G.
- **D18 The browser WS is read-only push; all mutations go over HTTP.** Simpler auth, CSRF and idempotency.
- **D19 A run row is created at claim, not at dispatch.** The dispatch lives in `dispatches` (at most one pending per card), so `runs.fence` is always the claimed fence and `UNIQUE(card_id, fence)` holds.
- **D20 `asks` is a separate table from `permission_requests`,** with one open ask per card enforced by a partial unique index. Permission requests may stack ("2 req").
- **D21 Codex is Phase 1.5.** `backend` accepts `codex_cli` in the schema, but the Phase 1 hub dispatches only `claude_cli` (`VALIDATION` otherwise).
- **D22 `approval` holds the MCP call open until answered.** Hence `MCP_TOOL_TIMEOUT=2100000` (35 min > T_park). The runner builder must verify the CLI honours it; if not, it chunks the wait and re-prompts, and records the finding here.
- **D23 Git allow rules.** Explicit `Bash(git add *)`/`Bash(git commit *)`… allow rules (spike 4b). Everything else outside the sandbox goes to `approval`.
- **D24 Pushes are allowed only to `origin board/<KEY>-r<n>` and the snapshot/salvage refs (supervisor-only).** Enforced by the `pre` hook as well as `--disallowedTools`.
- **D25 Web renders agent/human text as text.** No HTML injection path exists.
- **D26 No `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`; no secret in the CLI env instead (low admin + credential isolation).** CLI 2.1.285 with `SCRUB=1` forces permission mode `default` ("allowed_non_write_users hardening") and strips `*TOKEN*` vars from hook env. Evidence, two real `claude --model haiku` runs through the full profile against a fake hub, same six Bash commands (`ls`, `node --version`, `npm test`, `echo … > probe.txt && cat probe.txt`, `env | cut …`, `git status --short`), 2026-09-30:
  - **SCRUB=1** ($0.036): `system/init.permissionMode = "default"`. `ls`, `node --version` and `git status` ran (read-only, or the explicit git allow rule); `npm test`, the redirect and the `env` pipeline each went to `mcp__board__approval`, i.e. **3 of 6 routine sandboxed commands would have waited for a human**. So (a) `sandbox.autoAllowBashIfSandboxed` does **not** auto-allow under the forced `default` mode. (b) Explicit allow rules do work per command (the `Bash(git …)` rules), but every build/test/redirect/pipe shape would need one: an endless per-repo list, rejected. Bash saw no `BOARD_RUN_TOKEN`.
  - **SCRUB unset** ($0.053): `permissionMode = "acceptEdits"`, **0 approvals**, all six ran sandboxed, and a sandboxed `git commit` passed. (c) What SCRUB bought: Bash's `env` then listed `BOARD_RUN_TOKEN` (and the CLI's own `CLAUDE_CODE_MESSAGING_TOKEN`). So the fix is to keep secrets out of the env, not to scrub it: the run token moved to `<run_dir>/hook.token` (hook shim) and `mcp.json` (board-mcp only); `ANTHROPIC_API_KEY` moved to `apiKeyHelper` + `<run_dir>/api.key`; the private `BOARD_HOME` files are sandbox `denyRead` and disallowed for Read/Edit/Write. The env allowlist (D15) had no other secret. Residual: `CLAUDE_CODE_MESSAGING_TOKEN` is visible to Bash (the CLI's own local socket token, not a member credential). `apiKeyHelper` is unit-tested but not yet exercised live (the test member uses a subscription login).
- **D27 Repo identity = the configured origin URL** (`git config --get remote.origin.url`), not `git remote get-url` (§6.8). Deviation from design §9.4 #1, which named `get-url`: insteadOf is a local transport rewrite, and the member's configured name is the identity. Tests and the e2e harness rely on it (a bare remote reached through `insteadOf`).
- **D29 (P-1) One append-only journal, written in the same transaction as every mutation** (§15). Lean: no hash chain, no blob store, no bus cursors yet; comment bodies are not copied into it. Migration numbered 003 (002 was already taken by the device form factor).
- **D28 Plan approval is the card label `plan-approval`** (`states.PLAN_APPROVAL_LABEL`); the hub derives `ctx.require_plan_approval` and `offer.require_plan_approval` from it.
- **D30 Envelope hardening (security review L5).** The envelope moved to `shared/untrusted.js` so every package wraps the same way. Three changes: (a) a per-run random nonce in the tag name, so text on the board cannot guess the one closing tag that ends the data; (b) NFKC normalisation and removal of `\p{Cf}` / default-ignorable code points before closing tags are defused, so zero-width-split and fullwidth lookalike tags are caught; (c) board tool results are enveloped by the runner too (`board_get_card` was not: L5), with ids, enums and ages left bare. NFKC changes compatibility characters in the displayed data (e.g. fullwidth letters become ASCII); that is accepted, the text is data for the model and the board keeps the original.
- **D31 `board_create_card` creates only a To do child of the run's card** (plan item 15 `create_card`). Least privilege: same board, the run's repo, `parent_card_id` = the run's card (so `card:read` reaches it), `created_by` = the member the run works for, who must be able to write. The agent cannot pick a repo, board, labels, assignees, budget or column, and cannot dispatch it: a human must dispatch the card, so starting paid work stays a human action (row `1`). The child inherits the parent's policy labels, so it cannot shed `never_auto` or `plan-approval`. `cards.created_by_run_id` (migration 006) records the run; `CardView.agent_suggested` exposes it with `parent_card_id`, and the web shows an "agent-suggested" badge on the card so people see where it came from before they give it to Claude. Per-member hourly cap (`agent_card_member`). No new HTTP route: it is a runner RPC like its neighbours, with the same verification and journal.
- **D32 Lessons: a minimal append-only table** (plan item 15 `add_lesson`; migration `006_lessons.sql`). Rows are org- and repo-scoped (`org_id`, `repo_id`), carry the card, run and member, and can never be updated, deleted or replaced by `INSERT OR REPLACE` (triggers). Shape follows the local lessons prototype (`team-local/lib/lessons.js` on `feat/lessons-standup-local`: 10–500 chars, evidence ≤ 1000, starts as a suggestion). Deliberately missing for now: review/approval, votes, decay, and any read path. Nothing puts a lesson into an agent's context, so an unreviewed agent-written lesson cannot steer another run; review will be its own append-only rows. The journal row carries no text (like `comment.create`).
- **D33 Not on the board MCP: `claim_card`, `buddy_usage_history`, `buddy_health`.** A claim is the runner's fence CAS under the member's local policy (§6.4, T1), done before the agent exists; an agent-callable claim would let a model start paid runs on cards no human gave it, which §7.3 and row `1` forbid. The run's own card is already claimed when the agent starts. The two `buddy_*` tools read widget-local data (the Electron app's usage and health on the member's machine); board-mcp is a per-run proxy to the runner with no access to that data, runs under `--strict-mcp-config` in an isolated profile, and bolting the widget onto the board would break the package rule in §1. They belong on the widget's own stdio server (`mcp-server.js` at the repo root, which already has `buddy_status`, `buddy_spend`, `buddy_model_mix`, …).
- **D34 Plugin packaging (`board/plugin/`).** `.claude-plugin/plugin.json` (name `team-board`) and `.mcp.json` declaring the stdio server `board` as `node ${CLAUDE_PLUGIN_ROOT}/../mcp/server.js` with env `BOARD_MCP_PLUGIN=1` (format checked against the Claude Code plugin reference, 2026-09-30; `claude plugin validate` 2.1.286 passes). With that flag and neither run variable set, board-mcp connects, lists no tools and says why (its tools need a run's socket and token, D26); a missing variable without the flag, or only one of the two, still exits 1. Limits, recorded rather than worked around: (a) the runner never loads plugins (`--strict-mcp-config`, `--setting-sources ""`), so the plugin adds nothing to board runs; (b) a marketplace or git install copies only `plugin/` into the cache, so `../mcp` is missing there, and only in-place loading (`--plugin-dir`, a local-directory marketplace) works today. Real one-click value arrives with the hub's remote Streamable-HTTP endpoint (plan item 15, waiting on accounts), when `.mcp.json` becomes an `http` entry.
- **D35 Local auth (embedded hub).** `BOARD_AUTH=local` runs the hub inside the desktop app (Electron `utilityProcess` running `hub/server.js`; the app shows the hub-served web in a sandboxed view at `http://127.0.0.1:<port>`).
  - **Config.** The hub refuses to start unless `BOARD_BIND` is `127.0.0.1`, `::1` or `localhost` and `BOARD_PUBLIC_URL`, `BOARD_TUNNEL_PROBE_URL` and `BOARD_DEV_SEED` are unset. `BOARD_PORT=0` picks a free port.
  - **Secret.** A random 32-byte secret (hex) per launch, held only in memory. `BOARD_LOCAL_SECRET` (≥ 32 bytes, local mode only) overrides it, for tests only. It is never printed or logged.
  - **Port report.** When `process.parentPort` exists, after listening the hub posts `{type:'board.listening', port, hub_epoch, local_secret}` (`local_secret` only in local mode; other modes post the same message without it). A startup error (bad config, bind failure) posts `{type:'board.fatal', message}` and exits non-zero (2 for configuration, 1 otherwise). Without `parentPort` nothing changes.
  - **Auth.** A request is the local owner iff cookie `board_local` equals the secret (timing-safe). This covers every HTTP route (`/api/health` included), static files and browser WS upgrades; anything else is `401 UNAUTHENTICATED` (an upgrade is refused with HTTP 401). The dev-mode loopback guard applies too: proxy headers (`cf-connecting-ip`, `cf-ray`, `cf-access-jwt-assertion`, `x-forwarded-for`, `forwarded`) or a non-loopback `Host` → `403`. Same-origin checks are unchanged. Runner sockets (`/ws/runner`) keep device-token auth with no Access requirement, as in dev mode; devices are enrolled from the web as usual.
  - **Seed.** On first start with no members: one org (name from `BOARD_BOOTSTRAP_BOARD`, default `Me:ME`), board "My board" (that key prefix) and one owner with `email` null, `github_login` placeholder `local:<os username>` (reported as `null` on the wire, like `email:`), `github_id -1`, `display_name` = the OS username. Its id is kept in `hub_meta.k='local_member'` and every local request maps to it. A DB that already has members but no local owner refuses to start in local mode.
  - **Who am I.** The existing `GET /api/me` (`{member: publicMember, org, boards}`, all auth modes, same auth as other routes) serves; no `/api/whoami` was added.
- **D36 Integrations key over parentPort (local mode).** The desktop app keeps the integrations encryption key in macOS safeStorage and hands it to the embedded hub as `{type:'board.enc_key', key:<base64, 32 bytes>}` on `process.parentPort`, never via env. Local mode only; accepted once (`hub.setVaultKey`, memory only); the hub answers `{type:'board.enc_key', ok:true}` or `{ok:false, reason}` and never logs the key. Until it arrives the vault is unavailable (D41: no connections).
- **D37 The runner under the desktop app, and team presence.**
  - **D37a App mode.** Electron `utilityProcess` runs `runner/app-entry.js` (not `cli.js`: no detaching, no daemonising, the app is the supervisor). It reads **no** device file and **no** env secret (`BOARD_HOME` is ignored). It waits on `process.parentPort` for `{type:'runner.config', hub_url, device_id, device_token, cf_client_id?, cf_client_secret?, data_dir}` (`hub_url` `https:`/`wss:`, or `http:`/`ws:` only to `localhost`, `127.0.0.1` or `::1`; `cf_client_id`/`cf_client_secret` together or not at all; `data_dir` absolute, and it replaces `BOARD_HOME` for runs, worktrees, outbox, ledger, policy and the control socket; it is created 0700, `lstat`ed and refused, `runner.fatal` and exit 1, when it is a symlink, is owned by another uid, or still has any group/other bit after the `chmod 0700`, whose failure is itself fatal in app mode). The control socket `runner.sock` is created only inside a 0700 directory (else the supervisor refuses to start) and under `umask 0o177` around `listen()`, so it is never briefly wider than 0600 (tests: `runner/test/private-dir.test.js`, `runner/test/app-entry.test.js`). The credentials stay in memory and are used only as the §4.2 headers of the WS connect; they are never logged or echoed (test: `runner/test/app-entry.test.js`). Replies: `{type:'runner.ready'}` once the config is accepted and the supervisor started; `{type:'runner.status', state, detail?}` on every change of `state` ∈ `connected` (welcome received) \| `stopping` (quit begun) \| `backoff` (any other close or an unreachable hub; reconnecting) \| `unauthenticated` (close `4401`) \| `revoked` (`4403`) \| `unavailable` (`4503`, reconnecting; also `4426`, not reconnecting); a bad config → `{type:'runner.fatal', message}` and exit 2 (a later startup error: exit 1). A second `runner.config` is ignored. **Quit:** SIGTERM (or SIGINT) → `{type:'runner.status', state:'stopping'}`, then every live run is **parked**, not orphaned: the runner stops claiming (offers are ignored) and, per run at once, when the run has a CLI and the hub is connected, it follows the handover recipe (§6.7 `handover_begin`, window 10 s: the prompt at the next tool boundary or on stdin if idle, `board_write_handover` on the outbox at the current fence), then the stop recipe, the final snapshot pushed to `snapshotRef(KEY, fence)` (`refs/board/<KEY>/r<fence>`), then rpc `board_release{requeue:true, reason}` at the same fence (row `24`: → queued, fence+1, seeded from that handover; no `handover.complete`, no `run.failed`). A run counts as parked once the hub answers `state:'queued'`; it leaves the ledger. The whole quit is bounded by 25 s; then `shutdown({stopRuns:false})`, `{type:'runner.stopped', parked, parked_pending, orphaned}` and exit 0. `parked_pending` counts runs already inside a hub-requested park or handover window when the quit began (the hub has already moved the card on; the quit does not start its own handover over it). A fence that lands inside the quit's own handover window ends the run on the fence path (§6.9 salvage); the window's end then does nothing (no stop, snapshot or `board_release` at the stale fence) and the run counts as orphaned (test: `runner/test/quit-fence.test.js`). `orphaned` counts the rest (hub unreachable, no CLI yet, release refused e.g. `POLICY_DENIED` for `never_auto`, or the budget ran out): they keep their ledger entry and the next start's orphan recovery applies (stop recipe, local snapshot, `run.failed{supervisor crash}`), which is the rare path. Test: `runner/test/app-entry.test.js` (live fake run → SIGTERM → handover, snapshot, release, no `run.failed`; refused release → orphan on the next start). The CLI/device-file flow is unchanged.
  - **D37b Team presence.** App mode only. The app sends `{type:'runner.presence', enabled, share_summaries?, sessions:[{session_id, agent:'claude'|'codex'|'cursor'|'gemini'|'hermes', cwd, state:'working'|'waiting'|'idle', since, summary?}]}` (the latest wins). The runner maps each `cwd` to its repo's configured origin (D27, `git config --get remote.origin.url`), matches it against the `welcome.allowlist` (repos on the member's org's boards) and **drops** every session that doesn't match (default deny), then sends the `presence` frame (§6.2): `session_id` = HMAC-SHA256 with a random per-process salt (22 chars), `repo_id`, `branch` (omitted when detached), `state`, `since` (an ISO-8601 date-time with a zone, `Z` or `±hh:mm`, ≤ 40 chars, e.g. `2026-09-30T10:00:00Z`; the runner drops a session with anything else and the hub refuses a `presence` frame carrying one, `VALIDATION`), `summary` only when `share_summaries` is `true` (a separate opt-in from `enabled`, default `false`: otherwise no session carries a `summary`), through `redact` (repo paths → relative, other local paths → `<path>`, credentials → `<redacted:…>`; a local path is recognised after any character that does not continue a path segment, e.g. `file:///Users/…`, `cat</Users/…`, `x|/home/…`, `{/Users/…}`), then a presence-only pass (every home-style prefix anywhere, and every `/`-rooted run of 2+ segments → `<path>`), clipped to 120; each session passes `assertNoForeignBytes` or is dropped (a summary that still trips it is removed first). Never a `cwd` or an absolute path. On change at most every `PRESENCE_MIN_MS` (5 s), re-sent every `PRESENCE_KEEPALIVE_MS` (60 s) while enabled, and on every reconnect. No `runner.presence`, or `enabled:false`, sends nothing, except one `sessions:[]` frame (at once, or on reconnect) when the hub still holds something from this device. The hub keeps presence **in memory only** (never journaled, no migration), per device, dropped `PRESENCE_TTL_MS` (90 s) after its last frame (a disconnect just stops the frames), and immediately on `[]`, on the device's revocation (`DELETE /api/devices/:id`) and on its member's removal. Flood bounds on the hub: a non-empty `presence` frame arriving sooner than `PRESENCE_MIN_MS`/2 after the connection's last accepted frame is dropped silently (`[]` is always accepted); a frame only recomputes the boards of the device member's org; and a board's browsers get at most one `team.presence` per `PRESENCE_PUSH_MS` (1 s), a held-back change going out on the reaper's next pass (trailing edge, so the last state always arrives). A board's view (WS `team.presence`, `GET /api/boards/:board_id/presence`) groups sessions by member: only active members of the board's org, only sessions whose repo is linked to that board (`repo_short` = `repos.short_name`). Tests: `hub/test/presence.test.js`, `runner/test/presence.test.js`, `runner/test/app-entry.test.js`.
- **D50 Migration versions may have gaps; the FK-off directive.** Branches reserve migration numbers (007/008 are reserved elsewhere; accounts is `009_accounts.sql`), so `migrate.js` applies every shipped version missing from `schema_migrations` in version order, including a lower one that lands after a higher one; two files with one version refuse to load. A version already recorded in `schema_migrations` under another name (a DB that ran a branch's reserved number that main later gave to a different file, e.g. the integrations branch's `014_integration_requests`, now `017`) makes `migrate` throw before applying anything, instead of skipping the shipped file and failing later on its missing tables. A file whose **first line** is `-- migrate: foreign_keys=off` runs with `PRAGMA foreign_keys=OFF` set before `BEGIN IMMEDIATE`, runs `PRAGMA foreign_key_check` before `COMMIT` (any row → rollback and throw) and turns foreign keys back on either way (table rebuilds, design §2.1). 009 itself needs no rebuild: `members.user_id` is an added column; the members/devices rebuild (nullable GitHub columns, viewer → guest, device enrolments) waits for P2/P4.
- **D51 `BOARD_AUTH=accounts`.** access, dev and local are unchanged. Accounts refuses to start without `BOARD_SECRET`, without an https `BOARD_PUBLIC_URL` (a loopback bind may run without one, or with an http URL naming a loopback host), or off loopback without `BOARD_RESEND_API_KEY` + `BOARD_MAIL_FROM`; it takes no `BOARD_DEV_SEED` and `BOARD_BOOTSTRAP` only as a bare email. `BOARD_TRUST_CF_IP=1` (accounts only, loopback bind only) makes `CF-Connecting-IP` the client IP for rate limits, as Access mode already did. Dev hardening (design §9.5): `/api/dev/login` is only registered in dev mode, and dev refuses `BOARD_TRUST_CF_IP` like it refuses the public URL and tunnel probe.
- **D52 The desktop credential is a per-install device token, not access/refresh tokens.** Agreed with the app builder (it replaces the access-token/refresh-rotation brief): verify with `client:'buddy_desktop'` returns `device_token` = `bdt_` + 32 random bytes once, stored only as `user_devices.token_hash` (sha256 hex), the same `user_devices` row type the design's device flow (§6) uses, so P4 runners reuse it. Electron main injects `Authorization: Bearer <token>` into every request the in-app web view makes to the hub origin (webRequest), including the `/ws/board` upgrade; the page never sees the token. Bearer requests keep the Origin check but need no CSRF token (no ambient credential). It does not expire; it dies on sign-out, device revoke or account deletion, which also closes its sockets. Sign-up = sign-in (first verify creates the user with a verified email). CONTRACT ADDITION** (additive: the Resend, console and outbox mailers and every limit in `Accounts` are unchanged). `BOARD_MAIL_PROVIDER` picks the mailer: `resend` or `ses`; unset keeps the D66 rule (Resend when `BOARD_RESEND_API_KEY` is set, else none, or the console mailer on a loopback hub that is not exposed). `ses` sends through the Amazon SES v2 `SendEmail` API, `POST https://email.<region>.amazonaws.com/v2/email/outbound-emails` (source: https://docs.aws.amazon.com/ses/latest/APIReference-V2/API_SendEmail.html), JSON body `{FromEmailAddress, Destination:{ToAddresses:[to]}, Content:{Simple:{Subject:{Data, Charset:'UTF-8'}, Body:{Text:{Data, Charset:'UTF-8'}}}}}` (plain text only, never `Html`), signed with AWS Signature Version 4 in `node:crypto` (no SDK, no dependency): service `ses`, credential scope `<yyyymmdd>/<region>/ses/aws4_request`, empty canonical query, signed headers `content-type;host;x-amz-content-sha256;x-amz-date` (`;x-amz-security-token` added with a session token), the payload hash over the exact bytes sent, the date from the hub clock, the signing key derived from the secret for each request; - **D40 The journal is the event bus.** Integrations, the notifier and outgoing webhooks read the journal through per-consumer cursors (`bus_cursors`, migration 007) in `hub/bus.js`; they never hook into `apply()` and never update journal rows. Delivery is at-least-once and in order per consumer; a failing row is retried with backoff (1 s … 60 s) and blocks only its own consumer. A new consumer starts at the journal head (no history replay). The hub emits `journal` after every commit that wrote rows; `bus.poke()` drains on a later turn (`setImmediate`), never inside the committing code, and consumers run in the bus's own async context. The branch string is never parsed for a key; one with whitespace, control or format characters or over 255 chars is null, and so is anything ambiguous (two cards with that branch).   **Inbound webhooks**: `POST /integrations/<connection id>/webhook`, outside `/api`, no cookie or CSRF. Every id gets the in-flight read caps and the body read below, and an unknown, inactive, revoked or pending id is answered 404 only after that (D97, slice B3: the same work as a pending id, so the answers can't tell them apart); the in-flight read caps, which bound what an unverified sender can hold and never count failures: at most 4 body reads in flight per `<connection>|<client IP>` pair, 8 per client IP over every connection (so ≤ 8 MiB buffered per address) and 16 per connection; every id that is not a live connection (unknown, inactive, revoked or pending: the sender picks it) shares **one** pool of 32 reads in flight (`perUnknown`; so ≤ 32 MiB buffered for all of them together, however many addresses send), never a per-connection cap of its own, so a flood can fill it and a pending id's genuine `url_verification` then gets the 503 too (accepted: the provider or the admin retries); a sender whose network (its /24, or /48 for IPv6: providers send from pools) delivered a verified webhook to that connection within the last 15 minutes skips the per-connection cap, and so does an address inside the connector's declared `ingressCidrs` (the provider's published webhook ranges, e.g. GitHub's `hooks` from its meta endpoint; IPv4 /16 or narrower, IPv6 /32 or narrower, validated by `defineConnector`; `integrations.trustedIngress(connection, ip)`), so a flood from fresh addresses cannot crowd out the provider's own; only a delivery that verified **and took a fresh lease** vets its sender (a duplicate or `in_progress` answer does not), so replaying a captured signed delivery from anywhere vets nothing; over a cap → 503 `Retry-After: 1`, body unread (`config.webhookReads` overrides the numbers). Then the body (≤ 1 MiB, within 3 s of the start (`BOARD_WEBHOOK_READ_MS`; a webhook body is small and sent at once); over it → 413 (at once, unread and holding no read slot, when the declared `Content-Length` is over it; the same answer for every id), too slow → 408, both spending `webhook_fail_ip`; an unread remainder is not drained: the socket closes 1 s after the answer), then the connector's `verify()` over the raw bytes (constant time; failures are 401, logged, and spend `webhook_fail_ip`: 429 once the pair is over it), then the JSON parse (400). A delivery that verifies is never refused by `webhook_fail_ip`, and no failure count refuses a read before verification, so forged posts to a connection (from anywhere, including the provider's own shared IPs) can't block its genuine deliveries or another connection's. `mutate_ip` does not apply. The delivery is **leased** in `inbound_dedupe` under two keys, `<connection>:<verify().dedupe_key>` and `<connection>:body:<sha256 hex of the raw body>` (one transaction): the connector's key may rest on an unsigned delivery header, so a captured signed body replayed under a new delivery id still matches its body hash (identical raw bodies on one connection within 30 days are one delivery). A connector's `verify()` must return a dedupe key covering signed content or a signed timestamp where the provider gives one. Either key `done` → 200 `{duplicate}`; either key under a live lease → **503** `{ok:false, in_progress:true, retry_after_s}` + `Retry-After` (the lease's remaining time, 1–60 s), never 200: the running attempt may still fail and release the delivery, and a provider that got 200 for its retry would never send it again; otherwise both get a `processing` row with `lease_until` (handler timeout + 30 s), an expired lease being taken over. Only then is `webhook_conn` spent (per connection; a lease refused by the limit is released), so replays of a finished delivery spend nothing. Success → both rows `done`; a failed handler deletes them so the provider's retry runs. A connector may declare `ackEarly: true` (optional, default false; for a provider that needs an answer within seconds, e.g. Slack's 3 s): the delivery is answered 200 `{ok, accepted}` once it is verified, leased and has spent `webhook_conn`, and `handleWebhook` then runs under the same lease, timeout and `ctx` (a retry meanwhile gets the 503 above); since no provider retry follows, a failure (or timeout) is also written to `integration_audit` as action `webhook`, decision `failed`, a short `error` code and no ids or text, and the delivery is **marked done** (D42 addendum C2: a replay or manual redelivery of the same bytes answers `duplicate`); the hub waits for such handlers on shutdown (`hub.idle()`). If the hub process dies (crash, kill, power loss) after the 200 and before the handler ends, nothing is audited and the provider, which got 200, never retries: the event is lost until someone redelivers it by hand from the provider (e.g. GitHub's "Redeliver"), which runs once the lease (handler timeout + 30 s) has expired (a handler that ended, in failure too, leaves its delivery done instead: C2). Declare `ackEarly` only where the provider's deadline leaves no choice. Rows older than 30 days are swept (on insert, 1 in 100). Residual: after the sweep the same signed body is accepted again, so for a provider that signs no timestamp a captured request can be replayed after 30 days; a connector **must** enforce a timestamp window wherever the provider signs a timestamp (Slack: ±5 min), which closes it. Trade-off (L-5): two genuine events with byte-identical bodies on one connection within 30 days count as one delivery (the second answers `duplicate` and never runs). Every `handleWebhook` and `onEvent` has a 60 s timeout; on it `ctx.signal` aborts. A webhook handler that timed out keeps its lease (a retry answers 503 `in_progress`, never runs beside it); the row becomes `done` or is released when that call really ends, or the lease expires and a later retry takes it over. The bus never re-runs a row for a connection while its timed-out `onEvent` is still running: the call throws `handler_busy` (a `busy` error: retried with backoff, not counted toward `DEAD_AFTER`). If that timed-out call later succeeds, the registry remembers its seq for that consumer and the retry returns at once (cleared on use), so an external side effect is never repeated; if it fails, the row is retried as usual. A call that never settles is capped: after `BUSY_DEAD_AFTER` (30) busy retries on the same seq (backoff grows to 60 s, ≈ 25 min) the row is dead-lettered with `handler_stuck: …`, and the registry forgets the stuck call (its signal aborted at the timeout, so it can no longer act) so the connection's next row runs. The callback and webhook paths answer a generic 500 on any unexpected error. With Cloudflare Access in front, give exactly `POST /integrations/*/webhook` and `GET /integrations/*/callback` a **Bypass** policy (providers can't sign in); the signature and the signed state are their auth, everything else stays behind Access.
  **Bus**: one consumer per connection, `integration:<provider>:<connection id>`, subscribed on connect and at boot for active connections (starting at the head), unsubscribed on revoke, so one team's failing or slow tool never stalls or dead-letters another's. A row reaches a connection only when its `board_id` is a board of the connection's org: hub-wide rows (`board_id` NULL) and unknown boards reach none. The consumer is subscribed with `orgId`, so the bus selects only that org's boards' rows in SQL (`board_id IN (SELECT id FROM boards WHERE org_id = ?)`, served by `journal_board_seq`) instead of scanning every team's rows, and moves its cursor to the head it read up to (the registry re-checks the org per row).
  **Connect**: token (`POST …/token`; the error is fixed text) or OAuth/app install. `POST …/start` signs `state` = payload.HMAC(hub secret) with the admin, org, provider, a single-use nonce, a 10-minute expiry and the hash of a random `bind` (24 bytes, base64url, 32 chars); it returns `{url, bind}` and sets `bind` as the bind cookie: when the public URL is https, `__Host-board_int_<provider>` with `HttpOnly; SameSite=Lax; Path=/; Max-Age=600; Secure` (a `__Host-` cookie can be set neither over http nor by a sibling host, so nobody can plant their own bind); on an http dev/local hub, `board_int_<provider>` with `HttpOnly; SameSite=Lax; Path=/integrations/; Max-Age=600`. The callback reads only the variant that hub sets (on https a plain `board_int_<provider>` is ignored) and clears it with the same attributes and `Max-Age=0`. The signature is compared on decoded bytes. **The cookie is mandatory**: the callback refuses (400, "Open this link in the window Plexiform opened. The web renders a real `<form method="post" action target rel="noopener noreferrer">` with hidden fields and one submit button, "Create the app on <name>" (no auto-submit, no script), targeted like the connect window above (the desktop app's window-open handler sees a form POST open under the same name rules). Routes: see §5.2; a connection belongs to one org and every route checks it (revoked → 404).   **D42 addendum, the Sentry connector (Sentry slice S-A). Built in S-A (`hub/integrations/sentry/`, G1, `dailyCardCap`, `ctx.lastCreatedCard()`); the connector is registered by tests only and offered on no hub until the go-live gate below is passed. This entry is the rule it is reviewed against.** Additive: one new connector (`hub/integrations/sentry/`), two new optional spec fields (`showsWebhookUrl`, `dailyCardCap`), one new rate rule (`integration_card_day_conn`, spent only by a connector that declares `dailyCardCap`), one new pure read on `ctx` (`ctx.lastCreatedCard()`) and one new field on an admin's view of a connection (`webhook_url`); no migration, no new journal kind, no existing guarantee changes (GitHub, Slack and every connector without `dailyCardCap` are exactly as before). **Amended at the S-A build (2026-10-01, the hub owner's answers):** the daily rule is opt-in per connector; the timestamp header is informational and never refuses; the secret pattern is `^[A-Za-z0-9_-]{16,256}$`; the signature must be lowercase hex; a body that is not UTF-8 or has duplicate JSON keys is refused; the suppression comment goes only on a card this connection created that is not archived; the go-live gate keeps Sentry out of every hub's `connectorsFor`. The text below is the amended rule. Source for every Sentry fact here: Sentry's integration-platform webhook docs (`https://docs.sentry.io/organization/integrations/integration-platform/webhooks/` and `…/webhooks/issues/`, read 2026-10-01) and, where the docs are silent or wrong, Sentry's server source (`getsentry/sentry` master, read 2026-10-01: `src/sentry/sentry_apps/api/serializers/app_platform_event.py` `AppPlatformEvent.body`/`sentry_headers`, `src/sentry/sentry_apps/models/sentry_app.py` `build_signature`, `src/sentry/utils/sentry_apps/webhooks.py` `_send_webhook_request`, `src/sentry/utils/json.py`).
  **Connect.** `connect.kind: 'token'`. An org owner/manager creates a Sentry **Internal Integration** (permission Issue & Event: Read; webhook resource `issue`; nothing else) and pastes its **Client Secret** into the hub. The client secret is the webhook signing key and the only credential: no API token is stored, and `hosts: []` (the connector makes no outbound request at all: `verifyToken` checks the shape only and fetches nothing, `ctx.fetch` has no host it may reach). `verifyToken({token})` accepts only `^[A-Za-z0-9_-]{16,256}$` (else the D42 fixed token error, the value never echoed) and returns `external_id` = the first 16 hex characters of SHA-256 of the secret (stable per integration, so pasting the same secret twice into one team is the generic `CONFLICT`; the connector is not `workspaceUnique`, because the secret, not a workspace id, is the binding and each connection has its own URL; 64 bits of a hash of Sentry's long random secret tell a member who reads `external_id` nothing usable), `display_name: 'Sentry'`, `scopes: ['event:read']`, `secrets: {webhook_secret: <the secret>}` (the one declared kind, sealed by the vault, D41) and no `settings`. The secret is shown **nowhere** after the paste: not in any route, the token answer, the connections list, health, audit, journal or log; the web says so plainly next to the field ("Buddy keeps this secret encrypted and never shows it again. To change it, rotate it in Sentry and reconnect. Before you reconnect, rotate the secret in Sentry so that old signed requests can't be replayed to the new connection."). The Sentry org and project are not pinned at connect (the token flow sees no payload); the per-integration secret is the binding.
  **The webhook URL (gap G1).** The URL (`<public>/integrations/<connection id>/webhook`) exists only once the connection does, so the order is: create the integration in Sentry with any placeholder URL, paste the secret into the hub, copy the URL the hub then shows, edit the integration's Webhook URL in Sentry. A connector may declare **`showsWebhookUrl: true`** (a boolean; `defineConnector` refuses it on a connector that is not `connect.kind: 'token'` or has no `handleWebhook`; oauth/app_install connectors already get `webhookUrl` in `authorizeUrl`/`exchange`). For such a connector only, and only for an owner/admin caller, every connection object in `GET /api/integrations` and the `connection` in the `POST /api/integrations/:provider/token` answer carry **`webhook_url`**: `<public base>/integrations/<id>/webhook`, where the public base is exactly the one `/start` uses (`BOARD_PUBLIC_URL` without a trailing slash; on a `dev`/`local` hub without it, `http://<Host>`), or `null` when the hub has none (the list never fails over it). A member or viewer never gets the field (it is added in the admin branch, not by `publicConnection`), and `GET /api/integrations` `available[]` gains `shows_webhook_url: bool`. The URL is not a secret and is not treated as one: it is built from the connection id, which every member already reads in that list; hiding it from non-admins is only tidiness. **`verify()` is the gate, never the URL's secrecy.**
  **verify().** `verify({headers, rawBody, secrets, now})`: no `secrets.webhook_secret` → `{ok:false, reason:'no webhook secret'}`. Header `sentry-hook-signature` must be exactly 64 lowercase hex characters (Sentry sends `hexdigest()`; uppercase, other lengths and a repeated header are refused); the expected value is the lowercase hex HMAC-SHA256 of **the raw request bytes as received** (`rawBody`, never a re-serialisation such as `JSON.stringify(payload)`), keyed by the UTF-8 bytes of the client secret, compared with `crypto.timingSafeEqual` over two 32-byte buffers. Then the raw bytes must be valid UTF-8 and parse as JSON whose every object has distinct keys, else refused (401, nothing written): Sentry's `simplejson` body never has a duplicate key, and a body with one is exactly what two parsers could read differently. Header `sentry-hook-timestamp` is **informational only and never refuses a delivery** (absent, non-integer, stale or future all verify): it is not covered by the signature, so whoever captured a signed body can set any value, and a window on it would only refuse Sentry's own slow retries. When it is an integer more than one day from the hub's clock, the handler logs one fixed line without values, at most once an hour per connection. The replay controls are the dedupe and the signed freshness check below. `dedupe_key` = `body:` + the first 32 hex characters of SHA-256 of the raw body: signed content only. **`Request-ID` is unsigned and is never the dedupe key** (nor read for any other decision); `sentry-hook-resource` is unsigned too and only routes (an unknown resource or an action other than `issue.created` is verified, answered 200 and does nothing). No `parseBody`, no `ackEarly` (Sentry's documented deadline is 1 s; the S-A handler writes at most one card and one link and returns well inside it; if a real delivery shows otherwise, `ackEarly` is revisited then, not now).
  **Raw bytes: status of the evidence.** Sentry's docs show verification over `JSON.stringify(request.body)` (JavaScript) / `json.dumps(request.body)` (Python), i.e. over a re-serialisation, which this connector must not do: two parsers that disagree (duplicate keys, number forms, escapes) would let a body verify that the handler then reads differently. Sentry's source signs the same string it sends: `build_signature(self.body)` is HMAC-SHA256 over `body.encode('utf-8')`, and `_send_webhook_request` posts `data=app_platform_event.body`, where `body` is `sentry.utils.json.dumps` (simplejson, compact separators, `ensure_ascii` left at its default `True`, so the body is pure ASCII and its UTF-8 and wire bytes are the same). That establishes raw-byte signing **from the source, not from a recorded delivery**. **Go-live gate:** `sentry` is in no hub's `connectorsFor` (dev hubs included) and there is no flag to switch it on: until the gate below is passed it is registered only by tests. Before a hub operator adds it to `connectorsFor()` in `hub/integrations/index.js` (a one-line, reviewed code change), a **real** delivery from a Sentry org (issue created, at least) is captured with its exact bytes and headers, its signature is checked over those raw bytes under the real secret once, and only then is it re-signed under a fake test secret and kept as the fixture the tests use. **If the real signature does not match the raw bytes, the build stops and the hub owner is told; the connector is never adapted to verify a re-serialised body.**
  **Signed freshness and the 30-day residual.** `issue.created` fires when Sentry first sees the issue, so the handler acts only when the signed `data.issue.firstSeen` parses as an ISO-8601 date-time that is not more than 24 h before `now` and not more than 5 min after it; anything else is verified, answered 200 and does nothing. Since the dedupe rows live 30 days (D42), a captured body replayed after the sweep is older than 24 h by its own signed date and creates nothing; within those 24 h it is a dedupe duplicate. Independently, a card is created with `request_id = sentry-issue-<issue id>` and `integration_requests` (migration 017) holds `(connection_id, request_id) → card_id` **for the life of the connection**: nothing in the hub deletes those rows (no sweep; cards are archived, never deleted; a deleted team's connections are revoked, so their webhook is the unknown-connection 404), so any later delivery naming the same issue on the same connection returns that card, spends no card token (addendum C2) and the link is a no-op. **Residual:** a reconnect is a new connection id with an empty `integration_requests` namespace; if the admin reconnects with the **same** secret, a body captured from the old connection and replayed to the new URL within 24 h of its `firstSeen` verifies and can make one card per distinct captured issue, bounded by `integration_card_conn` and `integration_card_day_conn`. The web's reconnect text tells the admin to rotate the client secret in Sentry first.
  **Issue → card.** One card per Sentry issue. `issue.created` only (S-A); `data.issue.id` must match `^\d{1,20}$` and `data.issue.project.slug` `^[a-z0-9][a-z0-9_-]{0,63}$`, else nothing happens. Inside `ctx.act('sentry.card', {external_ref: 'sentry-issue-<id>'}, …)`, `s.actAs(ctx.connection.created_by).createCard(board, {request_id: 'sentry-issue-<id>', title, body, labels: ['bug']})` (no `meta.subject`: no provider user exists, so `integration_card_subject` does not apply), then `s.link(card, 'issue', '<id>', <link or nothing>)`. The board must be in `ctx.boardIds()` (checked before any `act()`); an unknown board is treated like no board (below). Labels: `bug` (an ordinary label) and `via:sentry`, which the registry adds through the reserved-label path (D42, D91; any `via:` the connector passed is dropped). The card starts in `todo` with no budget and no acceptance (F6, D42). **Board mapping** comes only from the admin's `settings.config` through `configKeys: ['default_board_id', 'project_boards', 'min_level', 'include_message']`: `project_boards[<slug>]` (an object of slug → board id) wins, else `default_board_id`; the board must be in `ctx.boards()` (else `createCard`'s own `NOT_FOUND`, spending nothing). **No board configured, or none for that project: nothing is created**, the delivery is answered 200 and counted for the hourly audit below; the connector never guesses a board. `min_level` (`fatal|error|warning|info|debug`, default `error`) drops issues below it.
  **Card text.** The DSN is public, so every string in an issue payload (title, message, culprit, type, release, environment, tags, user fields) can be written by anyone on the internet: all of it is hostile. The card is a **fixed template** of validated parts. Title: `Sentry: <type> in <culprit>`, `<type>` the issue's error class only if it matches `^[A-Za-z_][\w.]{0,60}$` (else `Error`), `<culprit>` scrubbed and ≤ 60 characters; total ≤ **120** characters. Body ≤ **1500** characters: the level (one of `fatal|error|warning|info|debug`, else the line is left out), the project slug (validated above), `count` and `userCount` as non-negative integers (Sentry sends `count` as a decimal string; anything else is left out), first seen as an ISO date re-formatted from the parsed value, the Sentry link (below) and one fixed line ("Suggested: press Tackle with AI to try a fix. A person starts it."). Never in a card, comment, link, audit, journal or log: the raw payload, the stack trace, tags, breadcrumbs, request data, contexts, release or environment strings that fail `^[\w.+@-]{1,64}$`, or any user field (id, email, IP, username). **The error message is off by default**: with `include_message: true` (a boolean config key) the title gets ` : <message>` from the issue's `metadata.value` (or `title`), scrubbed and ≤ **80** characters, still inside the 120 cap. **Scrub** (one shared, unit-tested function, applied to every free-text string that reaches the card, i.e. the culprit and the message; the type, slug, enums, numbers and date are validated, not scrubbed): NFKC; remove every `\p{C}` (control, format, bidi overrides and isolates, zero width, private use, unassigned) and `\p{Zl}`/`\p{Zp}`; collapse whitespace to one space; remove `<`, `>`, backtick, `[`, `]`, `*`, `~`, `|`, `#` (no markdown, HTML or links survive); replace mentions (`<@…>`, `<!…>`, `@channel`, `@here`, `@everyone`, `@<word>`), emails, URLs (any scheme), IPv4/IPv6 addresses, runs of 24+ `[A-Za-z0-9_-]` (token-like) and runs of 9+ digits (ID, card and phone numbers) with `[redacted]`; truncate on code points with `...`. **Link:** `web_url` is never taken on trust: it is used only if it parses as `https:` with no port, userinfo, query or fragment, a host that is exactly `sentry.io`, `us.sentry.io`, `de.sentry.io` or `<org>.sentry.io` (`<org>` `^[a-z0-9-]{1,50}$`), and a path `^/(organizations/[a-z0-9-]+/)?issues/<id>/?$` whose `<id>` equals `data.issue.id`; the link is then **rebuilt** as `https://<host>/issues/<id>/` (or the organizations form) from those validated parts, never copied. Otherwise the card has no link and is still created. **No connector text reaches an agent run except through the D30 envelope**: the card is `via:sentry`, so the runner wraps its title and body as `card:<KEY> … via sentry` in the nonce envelope (D30, D42); the connector writes no comment for an agent (an integration's comments are `source:'integration'`, `trusted:0`, never delivered) and no acceptance.
  **Flood control.** Every card spends `integration_conn` (120/min) and `integration_card_conn` (20/h per connection), and, for a connector that declares **`dailyCardCap: <integer 1–10000>`** (opt-in, checked by `defineConnector`; Sentry declares 100), also **`integration_card_day_conn`**: a new rule in `hub/ratelimit.js` `DEFAULT_LIMITS` (100 per 86 400 000 ms), whose capacity for such a connector is its `dailyCardCap` per 86 400 000 ms per connection (a token bucket like the others: the cap at once, then refilling over the day), unless the hub's `rateLimits` sets `integration_card_day_conn`, which then wins for every such connector; taken on `createCard` **after** `integration_card_conn` (an hourly refusal spends no daily token) and, like it, only after a D8 cache hit and a durable `integration_requests` hit are ruled out (addendum C2). A connector without `dailyCardCap` (GitHub, Slack, the fake) never spends it. Over either card rule the call throws `RATE_LIMITED` (that first refusal is audited `failed`/`rate_limited` by its `act()`, as today) and the Sentry handler **never throws for it** (answering 200; Sentry's retries would only add load): from then until the refusal's `retry_after_s` has passed it calls no `act('sentry.card')` at all, so a storm writes no audit row per event, and counts what it skipped in memory. **Suppression notice: one comment, at most one per UTC day per connection.** On the first such refusal of a UTC day, inside `ctx.act('sentry.notice', …)`, the connector posts one fixed-text comment ("Sentry is sending more new issues than this connection's card limit allows. New issues are not turned into cards until the limit refills; they are still in Sentry. The count is in this connection's Activity.") on the card the connection created most recently, read with **`ctx.lastCreatedCard()`** (a new pure read: the card of this connection's newest `integration_requests` row, `{id, board_id, archived}` or `null`; so always a card this connection created, also after a restart), and only if that card is not archived; with none, or an archived one, no comment is posted and nothing is audited for it. The `request_id` is `sentry-notice-<YYYY-MM-DD>`. A comment, not a card: a card would itself need the card tokens that are spent, and a comment spends only `integration_conn`. **Suppression audit: at most once per hour per connection**: the skipped count (cap and no-board, separately) is written as one `ctx.act('sentry.suppressed', {detail: {suppressed: <n>, reason: 'card_cap' | 'no_board'}}, async () => {})` per reason per UTC hour in which something was skipped (audited `auto`; ids and counts only; it writes nothing to the board). The in-memory counts and buckets reset with the hub process (a restart refills every bucket too, so a restart never suppresses more). Ingress needs nothing new: the M-1 read caps, 1 MiB / 3 s, `webhook_fail_ip` and `webhook_conn` (600/min) already apply.
  **What Sentry never does.** It never moves a card: `systemEvents: []`, `SYSTEM_EVENTS` unchanged, `ctx.system.event` never called; resolve and ignore change no column (S-B: a comment and a link status only). It never dispatches or starts a run (no action does; D42 already refuses `dispatch` to every integration); "Tackle with AI" is a person's button. **Autonomy actions** declared: `sentry.card` (default `auto`, `reversible: true`: it only creates a todo card a person can archive), `sentry.notice` (`auto`, fixed text), `sentry.suppressed` (`auto`, writes nothing). Nothing is `ask`, because nothing speaks for a person or reaches outside the hub. **Privacy:** what the hub keeps from Sentry is an error class, a project slug, counts, a date and a link (plus the scrubbed message only if an admin turns `include_message` on); `userCount` is an aggregate; no outbound request exists, so no new `privacy-flow` tag; S-A adds `sentry/index.js` to PRIVACY.md's `flow:integrations-hub` file list and one sentence saying the above.
  **Scope boundary.** S-A is: token connect, G1, `verify()`, `issue.created` → one deduped card + link, board mapping, the text rules, the daily rule and the notice/audit above, `connectorsFor` **not** enabling Sentry until the go-live gate. Later and not part of this entry: **S-B** (regression comment or "Regression of KEY" card, resolve/ignore comments and link status, the project → board map UI), **S-C1** (`metric_alert` critical → one incident card per episode), **S-C3** (`s.signal('incident', …)`, D99). Tests (S-A, failing first): forged, missing, wrong-secret, short, non-hex, uppercase and one-flipped-byte signatures; non-UTF-8 and duplicate-key bodies; stale, future, missing and non-integer timestamps all verify; dedupe stable for equal bytes and blind to `Request-ID`; replay after the dedupe rows are gone creates nothing (stale `firstSeen`, then the durable request); one card per issue id across different bodies; the injection corpus against the 120/1500 caps and the scrub; hostile `web_url`s; no board → nothing; the hourly and daily card rules; the notice once per day, only on an unarchived card this connection created; GitHub and fake connectors unaffected by the daily rule; G1 shown to admins only; the recorded real fixture (the go-live gate: S-A's fixtures are hand-made bodies signed at test time and are labelled so).

  **D42 addendum, start inputs: the GitHub organization. CONTRACT ADDITION** (additive, except the one `provider.org` rule marked below). A connector may declare `connect.startInputs: [name, …]` (1–4 distinct names `^[a-z][a-z0-9_]{0,39}$`, not `constructor` or `prototype`), only on an `oauth`/`app_install` connector without `connect.prepare`, together with `connect.startInput(name, value) → normalized string | null`; `defineConnector` refuses anything else. `POST /api/integrations/:provider/start` then takes `input` (absent or `{}`: none): not a plain object, a key the connector did not declare (any key, for a connector that declares none), a value that is not a string of 1–256 bytes, or a value for which `startInput` throws or answers anything but a non-empty string of at most 256 bytes (UTF-8, the normalized value too) is `VALIDATION` with a fixed text that never repeats the value, and no state, bind or cookie is minted. Like prepare, `/start`'s D8 replay entry is the fixed `409 CONFLICT {reason:'REPLAYED'}` ("This request was already sent. Reload the page."), whatever the replay's `input`, never the first answer: the request cache holds no org, state, form or bind. The normalized values reach `authorizeUrl`/`manifestForm` as `input` (always an object) for this start only, and are signed into the D42 state as `si` (omitted when empty), under the same MAC, expiry, single-use nonce and bind cookie, so they can be neither changed nor moved to another start. The callback refuses ("This link is not valid…") a state whose `si` is not a plain object of declared names whose values `startInput` returns unchanged, and passes them to `exchange` as `startInput` (`{}` when none). `exchange` may refuse with an error whose `code` is `NOT_OWNED` (the provider made the app under another owner than the one named at `/start`): only when the state carried start inputs, the callback answers `{ok:false, code:'NOT_OWNED', error}` with the registry's fixed text "<name> created this app under a different owner than the organization you named. Delete that app on <name> and start again." (never the connector's words; otherwise, and for any other throw, the generic "The provider did not accept the connection. Try again."), plus, when the error's `url` is https on the connector's `hosts` (no port or credentials), `link: {url, text:'Open that app on <name>'}`, which the callback page renders as one plain escaped link. The registry never stores such a value (`settings.config`, `settings.provider`), logs, audits or journals it; only what `exchange` makes of the provider's answer is kept (D42 addendum C1). **GitHub** declares `startInputs: ['org']`, a GitHub login (`^[A-Za-z0-9](?:[A-Za-z0-9]|-(?=[A-Za-z0-9])){0,38}$`: no leading, trailing or doubled hyphen, at most 39 characters), checked at start and again inside `manifestForm` (which throws on a bad one, so a path-like name never reaches a form). With an org the form posts to `https://github.com/organizations/<org>/settings/apps/new`; without one (empty input: no preference) to `https://github.com/settings/apps/new`, the signed-in account's own page, and the app name comes from the newest connection's `provider.login` only: **CONTRACT CHANGE:** a previous connection's `provider.org` no longer picks the owner, so the only org a form is ever sent to is one the admin typed, the state signs and `exchange` checks. `exchange` reads the code only from the callback's `URLSearchParams` and refuses, with code `NOT_OWNED` (`url`: `https://github.com/apps/<slug>`, built from the slug it checked against `^[a-z0-9](?:[a-z0-9-]{0,32}[a-z0-9])?$`) and nothing written, an app whose `owner.type` is not `Organization` or whose `owner.login` is not that org (compared without case). Without an org the owner is whoever GitHub says (recorded as provider facts, as for a first connect). **CONTRACT CHANGE:** `exchange` writes `provider.org` only when the app's owner is an `Organization` (its login); a previous connection's `provider.org` no longer carries over to a user-owned app. The org a connection ended up under is its `display_name` (the owner's login, shown to every member) and, for admins, `settings.provider.org`. The manifest asks for a private app (`public: false`), which GitHub lets only the account or organization that owns it install (to be confirmed on the first real connect), so a team's organization repositories need an app owned by that organization; moving to another owner means a new connection (accepted limit). The desktop connect window's manifest-POST check (`buddy-window/pages.js`) is unchanged.

- **D72 Integrations under `BOARD_AUTH=accounts` (merge of D40–D42 with D50–D71).** The `/integrations/<provider>/callback` and `/integrations/<connection id>/webhook` branches run after the dev/local loopback and local-cookie gates and before accounts auth, CSRF (`strictOrigin` + `X-CSRF-Token`) and the `/api` rate buckets: the signed OAuth state + bind cookie, and the delivery signature, are their only auth; the accounts `X-Frame-Options`/`frame-ancestors`/HSTS headers apply to them too (harmless on JSON and on the connect page). `/api/integrations*` are ordinary member routes: `resourceOrg` resolves `/api/integrations/:id` to the connection's team (unknown → 404 like any other resource), and `:provider` routes take the team from `X-Board-Team`/`?team=` or the caller's only team. The T-ROUTES matrix (D63) lists every integrations route; the pre-route paths (the connect callback, the webhook and, since D98, `/integrations/<provider>/identity/callback`) are listed apart with the reason they need no sign-in. `actAs` resolves the connection's `created_by` member row as before (accounts memberships are ordinary `members` rows) and spends `integration_conn`/`integration_card_conn`, never `mutate_member`. Deleting a team, or an account that soft-deletes a sole-member team, revokes that team's connections in the same transaction and erases their `connection_secrets` (`hub.revokeDeletedTeamConnections`): webhooks then 404 and bus consumers skip. `ratelimit.js` keeps both key helpers: `ipKey`/`netKey` for accounts and `failBucketKey` for `webhook_fail_ip` (both key IPv6 on its /64).

- **D105 Request limits (every auth mode). CONTRACT ADDITION.** The HTTP server takes `requestTimeout` 30 s (the whole request, headers and body, must arrive within it), `headersTimeout` 15 s, `keepAliveTimeout` **120 s** and checks open requests every 1 s (`connectionsCheckingInterval`), so a slowloris header or body trickle is cut (Node answers 408 and closes). ## 15. Journal (P-1, D29)

`journal` (migration 003) is the append-only record of every mutation: `{seq, board_id, card_id?, run_id?, at_hub, hub_epoch, actor_kind:'member'|'runner'|'system'|'integration', actor_id, kind, payload}`. `actor_kind:'integration'` (migration 008) has `actor_id` = the connection id: a row an integration caused (D42), either acting through a member (the payload then also carries `on_behalf_of: <member id>`, the member whose permissions were checked) or raising a system fact. `board_read_packet` reads the current run's own card only. `board_write_packet` requires current authenticated connection, enrollment, account/member, active run/fence, same linked repository and expected packet version. Staff use GET/POST `/api/cards/:card_id/packet`; writes require `expected_fence`, UUID `request_id`, `expected_version` and a closed six-field `data` object (brief, decisions, progress, nextAction, artifacts, reportedChecks). Viewer reads and staff writes stay in their current team; guests have no access. Archived cards/boards and packets from a previous repository are refused.

Versions are durable immutable context, limited to 100/card and 60 new writes/member/hour. Exact retries recheck current authority before returning a stored version; changed payload/request reuse fails. Server provenance records actual account/member/run/provider/fence. Participant reports are unverified; observed evidence is projected separately. Artifacts are permitted relative path reports or existing evidence IDs of this card, never fetched URLs/bytes. Text is scrubbed before storage and runner read/write results are nonce-enveloped as untrusted. No packet grants execution, approvals, scope, dispatch or resume; `packet.version` in the permanent journal stores metadata and content HMAC only.

The card drawer has Task context and Messages tabs. Context editing preserves the draft's packet version/fence through refreshes and version conflicts; discarding/reloading is explicit. Messages select a current same-team/repository peer and show host receipt separately from agent-reported acknowledgement. All participant content is rendered as text. Archived tasks and viewers have no editing composer; queued responses cannot fill a closed/reopened drawer or a later team/board/card. Browser requests retain stable request IDs across uncertain retries and throttle background context refreshes.

The native selected-board bridge adds `plexiform_read_packet`, `plexiform_write_packet`, `plexiform_list_messages` and `plexiform_send_message`. Write tools require a UUID request ID and current expected version/fence. Closed recursive schemas reject nested authority/unknown fields. Main derives a bounded repeated `board_id` query from its sealed grant; the server uses this only to narrow existing staff access, never as authority. Source, recipient, reply, delivery and peer projections honor these selected boards; source/repository/board filters precede bounded history/peer limits. Message retries recheck current recipient scope before returning the stored result. Native posts have staff provenance, provider/run null, no receipt capability/acknowledgement tool and no automatic wake, dispatch, approval or completion.

Acceptance uses actual accounts, enrolled protocol runners and real stdio MCP to write/read/retry packets and send messages; more than one page of hidden cross-board incoming messages cannot starve permitted history or inflate its truncation flag. Actual Chrome and sandboxed Electron verify durable editing, retained conflict drafts, scoped peers, transport labels and absence of renderer account credentials. The native local bridge does not establish remote OAuth service availability.

### Automatic observed work cards (040)

Accounts GET `/api/work-capture/routes` returns at most200 current staff team/active-board/exact-repository routes (`canonical_url`, team/board/repo IDs, role and scrubbed team/board names), with explicit `complete`/`truncated`. It grants no destination choice or capture permission. Main matches a locally observed canonical origin against all signed-in account catalogs, requires a remembered exact currently valid choice for ambiguity, and otherwise retains personal work plus needs-routing. No aliases, local paths, emails, transcripts or tool inputs leave through this catalog.

POST `/api/boards/:board_id/work-capture` accepts only install UUID, reported provider, bounded safe session/task identity, exact repo ID, scrubbed title≤200, observed status working/waiting/review/idle/ended and optional opted-in scrubbed summary≤2000. Accounts credentials must belong to the actual current member; credential/user/team/membership/write role/board/repository opt-in are rechecked inside the ordinary board queue before any existing mapping is returned. Team writes require an exact current repository row. Only the private embedded local owner may report personal no-repo work; runner, integration, legacy Access/dev and unknown grant authority are refused. These replay:false routes do not use the generic request cache.

Migration040 creates the card+durable source mapping atomically, deduplicated by actual user across team memberships and HMAC-only install/provider/session/task identities. A source is pinned to one board/repository; a different destination is409. There is no runner, dispatch, automatic for-agent comment, approval or completed-work authority. Working maps to In Progress, review/ended to In Review, waiting/idle preserve the last managed column (initially In Progress); never Done. Human edits permanently take precedence, including edits changed back, manual repository changes, and real run state. Archive/restore and deletion retain permanent tombstones. Empty-body POST `/api/cards/:card_id/work-capture/stop` can only stop the authenticated account's own capture; a current viewer may reduce their tracking.

Card projections expose separate `capture` metadata: reported provider (provider_verified:false), reported status and fresh status, tracking, server receipt time, monotonic age and per-field managed flags. Freshness expires after60 seconds and is unknown on reboot until a new authenticated report. `verified_run:false` and `grants_execution:false` remain explicit. New sources are bounded to20/user/hour and2000 lifetime mappings; reports120/user/minute and catalog30/user/minute supplement normal HTTP limits. The permanent journal contains capture provenance and text HMACs, including subsequent human edits; raw source IDs and briefs are absent.

Main rejects Git query/fragment origins and retains only a closed canonical repository name after removing userinfo. Every activity request requires a finite source change marker within60 seconds, rechecked after asynchronous routing; preferences and retries cannot renew an expired observation. Markers and providers remain reported, never verified liveness. Failed activity and missing-session idle requests share a durable15-second source cooldown, including across app restart. Idle only downgrades the reported state. Pausing or a personal override grants no destination rewrite.

Private capture storage keeps source/card/destination identities pinned, with at most2000 tasks/defaults and a2MiB UTF-8 ceiling shared by reader and writer. Closed metadata compaction drops unused fields without deleting identities. Saves check bytes and reserve acknowledgement growth before publication; refused or interrupted saves keep the previous file and memory and send no unpersisted new identity. Unreadable, public, symlinked or oversized state pauses capture with a visible notice, preserves the file for recovery and leaves the account app usable. It never silently resets the install UUID.

Acceptance: `hub/test/work-capture.test.js` exercises actual accounts and local-cookie HTTP, same-user cross-team/concurrent destination pinning, authority revocation after a held ordinary board queue, human edits/tombstones, injected transaction failure and SQLite restart durability. Desktop acceptance remains a separate integration gate.

### Task-bound communication (033)

`board_send_message` posts on the actual current run's own card, addressed to 1–4 exact active same-team/repository run IDs discovered by `board_list_messages`. It derives sender account/member/device/provider/fence from server records, never from caller claims. Cross-board peers share the exact repository row and team; matching canonical URLs in another team grant nothing. Closed staff GET/POST `/api/cards/:card_id/messages` use live credentials and membership; viewer reads, guest absence, `expected_fence` on writes, durable actor/request/payload retries and queued rechecks match packets. Body text is scrubbed before storage, retained as an ordinary comment with `for_agent=false`, and never auto-dispatches, resumes, answers a human ask or changes approvals. Runner read/write text and names are nonce-enveloped as untrusted.

Threads originate on the hub, at most one origin/run. Joining one requires replying to a message sent by or addressed to this current run/fence. Omitting IDs cannot reset that thread's budget; depth is at most 3, with at most 8 run-origin messages and 32 total messages/thread, 1000 messages/source card, and the shared 60-new-writes/member/hour bucket. Readers return bounded inbox/history/peer lists, with a 60/minute member read limit. Questions needing a human remain `board_ask_human`.

Delivery is pending until the live supervisor receives the inbox response and reports it with runner-only `runner_messages_received`. It passes the server-issued receipt ID/token to the current authenticated socket, run/fence and server connection generation; the agent cannot select a generation. `board_ack_message` is a separate participant-reported acknowledgement after host receipt, never verification of work. Replaced connections, revoked enrollment, stale fences and other runs cannot report or acknowledge old delivery attempts. Reconnect issues a fresh attempt (at most 8 retained per exact delivery); no raw token is stored, journaled or shown in staff views. `message.create` journals IDs/kind/content HMAC only, and `message.receipt` journals bound IDs/state/source only. Receipt capability copies are scrubbed from participant text.

### Expiring advisory ownership (038)

`board_declare_plan` stores at most 200 relative file/directory intents (literal or terminal `/**` prefix) and `board_check_overlap` returns the current intent, at most 50 same-team/exact-repository intents and matching prefix overlaps. Paths and participant names read by a model are nonce-enveloped as untrusted data. Each projection contains at most 20 paths with an explicit truncation flag; unrelated boards are filtered in SQL before the bounded limit when private server options supply `boardIds`. `hub.ownership.staffRead(member, cardId, cred, {boardIds})` provides current staff/viewer reads and revalidates credential ownership, membership, team and active card/board inside the ordinary board queue. Accounts mode requires a real current staff credential; guests are absent. This checkpoint adds no public HTTP/native route or execution tool. Remote grant adapters must also validate their own live grant inside this queue before calling the projection.

Migration038 captures actual run/account membership/device/provider/repository/fence and plan requirement at run creation; those identity fields are immutable. Historical runs lacking a record start conservatively with a required plan. Removing a later card label cannot widen that requirement. Editing is shown only for a current authenticated registered connection with live enrollment/member/account/repository opt-in, current run/fence, an accepted heartbeat from that exact server connection generation, an open host gate and live child, and an unexpired 30-second monotonic lease. A host-reported read-only generation narrows the projection; it cannot bypass a required recorded human plan approval. Approval is rechecked against current approver membership/role/policy on every renewal and read.

Ownership projection reads share a 60/minute token bucket per actual member across staff credentials, runner connections/runs and declaration responses. The member is derived from current authority before consuming the bucket. Exhausted declarations fail before changing ownership, planned paths, journal or permission state; ordinary queued authority rechecks remain required. Matching normalizes each bounded source path once and traverses a segment index per peer, preserving parent/child and terminal `/**` semantics without an own-path × peer-path comparison loop. Only one peer index is retained at a time; original path order and truncation remain visible. This bound covers the ownership projection; the separate legacy overlap classification engine keeps its existing behavior.

Server-minted ownership generation and hub epoch are coordination identifiers, never bearer authority. Expiry, hub restart and connection replacement invalidate live editing until a fresh accepted heartbeat rotates the server generation. A stale revision or empty-path release fails without overwriting current intent; the supervisor privately reads the server generation before declaring. A new declaration returns to planned until its next eligible heartbeat. Terminal/revoked/fenced/dead/closed-gate workers retain at most planned context, and an ended current-fence task in review can retain awaiting-review context. These records are advisory warnings: `grants_execution=false`, `global_filesystem_lock=false`; they never dispatch, resume, approve, integrate, merge, or widen the Git/worktree sandbox.

### Sentry status and incident source preparation

Sentry remains absent from the shipped connector catalog until independent source and actual provider acceptance. Signed issue resolution/archive/regression deliveries comment only on a live connection-owned issue link; they never dispatch, move, reopen, or finish the card. Metric critical deliveries create one Todo incident per alert-rule id and fixed cooldown bucket of signed `date_started` (default 60, configured 1–1440 minutes), with each provider incident id durably linked for later warning/resolved/critical observations. All projects must select the same active team board; an absent explicit default or conflicting map pauses creation. Long-running metric incidents have no 24-hour age rejection; permanent episode requests/links coalesce previously observed incidents. Issue creation retains its signed `firstSeen` freshness rule. Provider status order is not inferred from `lastSeen` or unsigned headers: stored status describes hub-observed changes only.

Only Sentry's exact declared `sentry.status` and `sentry.incident-status` actions may call private `actAs(created_by).observeLink(cardId, kind, externalId, {state}, {request_id,body})`. Its WeakMap-branded immutable primitive context binds current captured connection/member/user/action, exact issue/alert link and a dedicated kind/id/64-hex-event request id. JSON/MCP/HTTP cannot supply this capability or callbacks. The existing `Api.comment` queue owns the operation; inside its ordinary synchronous transaction current writer/connection/action/settings/link/card/archive checks precede durable replay. New comments, 046 receipts and fixed Sentry link status commit together; rollback leaves all three absent. Same-state observations write only a new receipt pointing to an already connection-owned 046 receipt's same-card untrusted non-agent integration comment. Missing or tampered pointers produce a legitimate new observation instead of adopting foreign comments. Coalesced writes require storage but spend no comment-row quota and produce no comment/feed/broadcast. Durable replay can read an existing receipt under storage pressure and cannot rewind later status. Fixed stored state/hub observation time/private comment id fit the existing 512-byte status column; the private pointer is omitted from `ctx.linkStatusFor`. PR status, ordinary comments, public endpoints and applied schemas are unchanged. D99 incident signals/notifications and outbound source closure remain separately gated work.
