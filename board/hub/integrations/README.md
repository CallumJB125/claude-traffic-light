# Writing a connector

A connector is one ESM module under `hub/integrations/<id>/index.js` that
default-exports `defineConnector({...})` (see `connector.js` for the full
shape, and `fake/index.js` for a complete, tested example). Add it to
`connectorsFor()` in `index.js`.

The registry (`registry.js`) does everything around it. **Don't re-implement
these in a connector:**

| Concern | Where it lives |
|---|---|
| Sealing tokens/secrets | `createConnection({secrets})` → vault (AES-256-GCM, key never in the DB, D41). Read them with `ctx.secret(kind)`. Declare every kind in `secrets: [...]`; every value must be a non-empty string ≤ 16 KiB (a PEM key fits), else the connection is refused (`VALIDATION`) and nothing is stored. Key rotation (`BOARD_ENC_KEY_PREVIOUS`) re-seals every row at startup (one transaction, counts logged), and any row still left on read; a secret no key opens makes the webhook answer 500 before `verify()` runs (health `vault_error`, written at most once a minute per connection). |
| Webhook ingress | `POST /integrations/<connection id>/webhook`: every id's body is read under the caps below; an unknown, inactive, revoked or pending id is then 404 (identical for all of them; the registry does the same work, D97); failed signatures, bodies over 1 MiB (413) and bodies not received within 3 s (408; `BOARD_WEBHOOK_READ_MS`) spend a failure budget per connection + client IP (an IPv6 client's /64): past it failures answer 429, but a delivery whose signature verifies is never refused by it; before the signature is checked only in-flight read caps apply (4 per connection + IP, 8 per IP, 16 per connection, 32 for every non-connection id together; a sender whose /24 (IPv6: /48) delivered a new verified webhook in the last 15 min skips the connection cap; a replayed duplicate vets nothing), over one → 503 `Retry-After: 1` unread; raw body ≤ 1 MiB; the per-connection rate limit is spent only by verified deliveries that are not duplicates. Your `verify()` must check the provider signature over the **raw bytes** in constant time and return `{ok, dedupe_key}`. Bad signature → 401 + a warning log (and spends that failure budget); nothing runs. The body reaches your handler as `payload`, `JSON.parse`d (invalid JSON → 400); a provider that posts something else (Slack: `application/x-www-form-urlencoded`, interactive payloads in a `payload=` JSON field) declares `parseBody({rawBody, headers}) → payload`. It runs **only after `verify()` passed**, synchronously; a throw, anything but a plain object (arrays, Promises, class instances are refused) or an own top-level `__proto__`/`constructor`/`prototype` key → 400 `VALIDATION` with a fixed message, nothing leased or run. Dedupe keys never depend on it. Don't merge the payload into other objects (nested keys are not checked). |
| Per-user command limit | Optional `rateSubject({payload, headers}) → string \| null` (D42 addendum C3): the provider user a delivery is for (Slack: a command's `user_id`, an interaction's `user.id`; `null` for events). Called synchronously after `verify()`, `parseBody` and a fresh lease (a replayed duplicate never reaches it); a throw or anything but a 1–128 char string is `null`. A subject spends `integration_user_cmd` (30/min per connection and that user, keyed on `hub.refHash`, never the raw id) before `webhook_conn` and your handler. Over it, nothing runs, the lease is released and the answer is 200 with `ackBody({payload, headers, rateLimited: true})` (your fixed "slow down" text; never reflect request data) for a delivery that is early (`ackEarly` true for it), else 429 `RATE_LIMITED` + `Retry-After` (no `ackBody`, or a late delivery: a 200 would drop the provider's retry); it is audited `webhook` / `failed` / `rate_limited` at most 6 times a minute per connection. Card creation keeps its own limits inside `act()` (`integration_card_subject` 5/h per the same user, `integration_card_conn` 20/h). |
| Provider ingress ranges | Optional `ingressCidrs: ['192.30.252.0/22', …]` (IPv4 /16 or narrower, IPv6 /32 or narrower; refused otherwise): deliveries from these addresses skip the per-connection in-flight read cap, so a flood can't crowd out the provider even before it has delivered once. They still need a valid signature. **You own the list**: take it from the provider's published ranges (GitHub: the `hooks` array of `GET https://api.github.com/meta`) and refresh it when the provider changes them; a stale list only loses the head start, never lets anything unsigned in. |
| Timestamps | If the provider signs a timestamp, `verify()` **must** enforce a window (Slack: `X-Slack-Request-Timestamp` within ±5 min of `now`) so a captured request can't be replayed after its dedupe row is swept. |
| Replay protection | Each delivery is keyed twice in `inbound_dedupe`: `<connection>:<dedupe_key>` and `<connection>:body:<sha256 of the raw body>`, so a captured signed request replayed under a new (unsigned) delivery id is still a duplicate, and identical raw bodies on one connection within 30 days count as one delivery. **Your `verify()` must return a `dedupe_key` that covers signed content** (an event id from the signed body) **or a signed timestamp** where the provider gives one, not only an unsigned delivery header. A finished duplicate spends no `webhook_conn`. The registry leases both keys while your handler runs: a concurrent duplicate gets **503** `{in_progress}` + `Retry-After` (never 200: if the running attempt then fails, the provider must still send it again), a finished one `duplicate`; a failed handler releases it so the provider's retry runs (a provider that needs an ack within seconds, like Slack, can declare `ackEarly: true`, or per delivery `ackEarly({payload, headers}) → boolean` (called after `verify()` and `parseBody`; only `true` is early, a throw or anything else answers late), to get 200 `{accepted}` once verified and leased, then your handler runs under the same lease (with `ackBody({payload, headers})` you choose that 200's body: `undefined` → empty, a string → `text/plain`, a plain object → JSON; over 4 KiB, another type or a throw → empty; called synchronously before the handler starts; **never reflect request data in it**, except a verified `url_verification` `challenge`); a failure (or timeout) is audited as action `webhook` / `failed` + code, since no provider retry follows, and the delivery is **marked done**, so a replayed or redelivered copy of the same bytes answers `duplicate` (declare `onAckedFailure({payload, headers, error_code, fetch})` to send a fixed-text "couldn't do that" reply then: called once, after the audit, with a short code only and the restricted fetch, ≤ 10 s, errors swallowed; it can't change the answer already sent); **if the hub crashes or is killed while that handler runs, the event is lost** (nothing is audited, the provider got 200 and won't retry) until someone redelivers it by hand from the provider once the lease has expired, so use `ackEarly` only when the provider's deadline forces it); an early delivery whose handler times out is marked done at the timeout, even if the handler never settles (so no copy takes the lease over once it expires); a late handler that timed out keeps the lease until it ends (it may still be running); a late delivery's failure still releases it for the provider's retry. Rows are kept 30 days. **Residual:** once the sweep deletes them, the same signed body is accepted again, so for a provider that signs no timestamp a captured request can be replayed after 30 days; where the provider signs one, your `verify()` **must** enforce the window (see Timestamps), which closes that. **Trade-off:** two genuinely distinct events with byte-identical bodies within 30 days are one delivery (the second is answered `duplicate` and never runs); providers put an event id or timestamp in the body, so this should not happen, but don't rely on repeated identical bodies. |
| Idempotency | Neither the dedupe row nor the D8 `request_id` cache (in memory, 10 minutes, lost on restart) is durable idempotency. `createCard` is: the registry records `(connection, request_id)` → card in `integration_requests` (migration 017) in the same transaction as the card, so the same `request_id` always returns the same card (after a restart, a crash before you linked it, a swept dedupe row, concurrent duplicates); derive it from the external id. A `request_id` is at most 200 chars (longer is `VALIDATION`, never cut), and the same one aimed at another board than its card's is `CONFLICT`. Comments and actions have no such table: handlers **must** still be idempotent through links: check `ctx.linked(kind, externalId)` before acting, and link what you create. |
| Board events | `consumes: [journal kinds]` + `onEvent(row, ctx)`, via the bus: one consumer per connection (a failing connection never blocks another team's), at-least-once, in order, retried with backoff, dead-lettered after 8 failures (≈ 3 min). Only rows of boards of the connection's own team reach it (never hub-wide rows); the bus selects them in SQL, so other teams' traffic costs your consumer nothing. Be idempotent. |
| Timeouts | `handleWebhook` and `onEvent` fail after 60 s. `ctx.signal` aborts when the handler ends (returns, throws or times out; `ctx.fetch` uses it; check it in long work): after that `ctx.act`, `ctx.fetch` and `ctx.system.event` throw `this handler has ended`, so a `ctx` kept past its handler is dead. The bus never runs a row again while its timed-out call is still running; if that call later succeeds, the row counts as done (not run again); a call that never ends is dead-lettered (`handler_stuck`) after 30 busy retries (≈ 25 min), and the next row runs. |
| Acting on the board | Only inside `ctx.act(action, meta, async (s) => …)`: `s.actAs(memberId)` → `createCard / comment / action`, the same Api methods and D8 `request_id` replay cache as the web (ids are namespaced per connection), limited per connection (`integration_conn` 120/min; `createCard` also `integration_card_conn` 20/h, neither card bucket spent when `integration_requests` already holds that `request_id`), never the member's own `mutate_member` bucket. Name the provider user an action is for as `ctx.act(action, {subject: '<provider user id>', …}, run)` (a string ≤ 128 chars, else `VALIDATION`): its `createCard`s are then also limited to `integration_card_subject` 5/h per (connection, subject), checked first, so one user can't spend everyone's cards. Only a keyed hash of the subject is kept (never audited, journaled or logged); a D8 replay spends nothing. Pass it for anything a public user triggers (a Slack slash command or shortcut). Over a limit the call throws `RATE_LIMITED` and the action is audited `failed`. Every call **requires** a stable `request_id` derived from the external id. `s.link(cardId, kind, externalId, url)` links a card of your team (there is no `ctx.link`). `s.linkStatus(cardId, kind, externalId, {state?, checks?, review?})` merges a partial status into a link **this connection** already has on that card (else `NOT_FOUND`): only `state ∈ open\|draft\|merged\|closed`, `checks ∈ passing\|failing\|pending\|none`, `review ∈ none\|requested\|changes_requested\|approved` are kept (`connector.js` `LINK_STATUS`); other keys and values are dropped without touching the stored ones, nothing valid left is `VALIDATION`, the merged blob is ≤ 512 bytes. Send only what changed (`{state}` from a PR event, `{checks}` from a check suite, `{review}` from a review). It also keeps `head_sha` (exactly 40 lowercase hex, else dropped like any bad value), which the card face never shows: `ctx.linkStatusFor(cardId, kind)` → `{external_id, state?, checks?, review?, head_sha?} \| null` (the newest link of that kind this connection has on a card of your team; a pure read) gives it back, so store the head from each PR event and drop a check suite whose `head_sha` is not the stored one (a late result for an older push). The card view's `pr_link_status` shows the newest `pr` link's `state`/`checks`/`review`. The scope, and every handle `actAs` returned, stops working once `run` returns; a call `run` started without awaiting is awaited before `act()` returns (if it fails, the action is `failed`), so nothing lands after the scope closed; each call re-checks the member. `actAs` takes, inside an `act()` that names a `subject`, only `ctx.memberFor(subject)` (that user's member linked on this connection, D98), and inside one without a subject only `ctx.connection.created_by`; always with at most `member` rights. `action` allows only `cancel`, `stop` and `approve_done` (the last only inside an act() action you declared `ask`); everything else — dispatch, retry, take over, hand over, request changes, answer — is `POLICY_DENIED`. `createCard(boardId, body)` takes a board of your team only (another team's or an unknown id is `NOT_FOUND` before any rate token is spent), always starts the card in `todo` (any `column` you pass is dropped), ignores `budget_usd` (a budget stays a person's call) and labels the card `via:<your connector id>` (any `via:` label you pass is dropped): the web shows it as a "via <id>" badge and the agent's envelope source says `via <id>`. `comment` refuses `for_agent: true`; your comments are `source: 'integration'`, untrusted, and never reach an agent. Answering a permission request is refused. |
| Autonomy + audit | Declare each action with its default in `actions` (`auto` for facts; `ask` for anything that speaks for a person, writes externally or touches production). Admins can change it per connection. `auto` is audited `attempted` → `auto` or `failed` (+ short code). `detail`/`undo` keep scalars and id-shaped strings only (`^[\w.:#\/@-]{1,128}$`; free text is dropped silently; ≤ 2 KB); `external_ref` is cut to 80 chars, control/bidi characters stripped. Only admins read the audit log; rows are kept 90 days. |
| Who did it | Permission checks use the member you act as (usually `ctx.connection.created_by`); the journal records `actor_kind: 'integration'` with your connection id, and the feed names your connector. If **`created_by`** is removed or becomes a viewer, the webhook answers 200 and health says `actor_unavailable` until an admin reconnects. A **linked member** who was removed, demoted or left (D42 addendum C2) makes `actAs`/its calls throw `ACTOR_UNAVAILABLE` with `scope: 'member'` (audited `failed` for that act): catch it and answer the user with fixed text; if you let it escape, the delivery is done and answered exactly like a success, with no health change. Check first with `ctx.linkState(subject)` → `'active'` (acts), `'unavailable'` (linked, but can't act now: say so), `'none'` (not linked: "link your account first"); it reads this connection only and never returns a member id. |
| Reading the board | Pure reads on `ctx` (no `act()` needed, nothing written): `ctx.boards()` → `[{id, title}]` (your team's boards, by title, at most 100) for a board picker, and `ctx.card(id)` → `{id, key, title, board_id, column_name} \| null` (a card of your team; never its body, acceptance, labels or budget; another team's or an unknown id is `null`). `ctx.boardIds()` stays. Post a card's title only where its team can see it. |
| PR ↔ card links | Only through `ctx.cardForBranch(repo, branch)` → `{card_id, base_ref} \| null` (`base_ref`: the base branch the matching run recorded, `runs.base_ref`; a PR from that branch into any other base is not the card's review, so compare it with the PR's base before linking), then `s.link(card_id, 'pr', …)` inside `act()`. **One `pr` link per card per connection**: a second `pr` link on the same card is `CONFLICT` (re-linking the same external id is a no-op), even once the first PR is closed. **Once the card has a verified PR** (`ctx.verifiedPr`), its slot takes only that PR, named by `url`: the PR's own https `<repo>/pull/<n>` html URL, whose number and repo must be the verified PR's (bound exactly as `ctx.system.event` binds them; the external id is never read). Anything else (another number, the same number in an alias or mirror repo, no `url`, http, a query string) is `CONFLICT`, for `s.link` and `s.relink` alike, so always pass the html URL; a link made before the verification stays. The slot moves only through `s.relink(cardId, 'pr', oldExternalId, newExternalId, url)` (in the scope, same card/connection scoping as `link`; one transaction): once the card has a verified PR, only to that PR (the rule above, whatever the old link's state), so a squatter's early open PR never blocks it; before that, only off a link whose stored `state` (`s.linkStatus`) is `closed`, to any PR (a `merged` link is final, so someone with push access opening another PR from the board branch never takes a done card's slot; no state, `open` or `draft` is not ended either); else `CONFLICT`. The card's current link not being `oldExternalId` is `CONFLICT` (no `pr` link at all: `NOT_FOUND`), a new id already linked to another card is `CONFLICT`, any kind but `pr` is `VALIDATION`, and a swap to the id the card already has is a no-op. The old row is kept as kind `pr_superseded` with its status (the latest one per external id), so it no longer finds the card (`ctx.linked('pr', old)` is `null`) or shows on it. **Fork rule:** a PR is the card's only when its head repo is its base repo (GitHub `head.repo.id === base.repo.id`; a deleted head repo, `null`, is not): never link or act for a PR from a fork, even with the card's branch name, since anyone can open one (the hub verifies evidence the same way, D90); `ctx.linkedByCard(cardId, 'pr')` → `external_id \| null` reads the one you have (this connection, your team's card; a pure read like `ctx.linked`). `ctx.verifiedPr(cardId)` → `{number, repo, url} \| null` is the card's newest `hub_verified` PR evidence (the PR the hub checked with GitHub and its merge poll watches; `repo` (`owner/name` on github.com, else `host/owner/name`) and `url` come from the card's repo on the hub, never the runner's text; another team's card, a card with no repo, or unreadable evidence → `null`): link and act only for that PR. `repo` is the payload's `owner/name` (github.com; or `host/owner/name`), matched case-insensitively against a repo linked to a board of your team; `branch` must **equal** a branch the board recorded for a run (`runs.branch`, `shared/fence.js` `branchName()` → `board/<KEY>-r<fence>`) in that repo, on a card of your team. Nothing is parsed out of the string: a lookalike (`board/BDL-1-r9` with no run 9, other case, a suffix, `..`), any whitespace/control character, over 255 chars, another team's card, or two cards with that branch → `null`. It is a pure read (on `ctx`, not the act() scope). **Never** link from free text such as "Fixes BDL-12" in a title or body: anyone who can open a PR could then move any card. |
| System facts | `systemEvents` + `ctx.system.event(type, {kind, external_id, pr, by, repo})` for a card linked to this connection. `pr` must be an integer, `by` a GitHub login (else dropped), `repo` as for `cardForBranch`. **Bound to the hub-verified PR**, like the merge poll: applied only when the card has `hub_verified` PR evidence, `pr` equals its number and `repo` names the card's repo (its repo row's `canonical_url`, never one of its aliases, which may be another repo such as a mirror where anyone can open a PR with that number; `ctx.verifiedPr` takes repo and URL from the hub, never the runner's text, so always pass `repo`); else `{done:false, reason:'no_verified_pr'}` (no such evidence: an integration never moves such a card) or `{done:false, reason:'not_the_verified_pr'}`, audited `failed` with that code, before autonomy is consulted (a decoy never becomes an `ask` suggestion), and checked again inside the board queue. So a second PR from the card's branch into another base, merged or closed unmerged, moves nothing. **Never call it from inside a `withBoard` callback on the same board** (it waits on that queue: deadlock; the hub throws instead). |
| HTTP out | Declare `hosts: ['api.example.com']` (exact hostnames, https only). `ctx.fetch(url, init)` refuses any other host, follows one same-host redirect at most, 10 s timeout, retries 5xx/429 honouring `Retry-After`, records health. `connect.exchange` / `verifyToken` get the same restricted fetch. |
| Health and errors | Health keeps a short code (members can read it). Your error messages are logged redacted and never shown to users, so don't bother making them friendly — and never put secrets in them. |

**Never** journal or audit secrets, tokens or external message text (D41): ids and short
labels only. The registry already keeps a card you create out of the journal: its `card.create`
row holds keyed hashes (HMAC under a per-hub key an operator can erase) of the title, body and
acceptance, never the text, and of your `external_ref`, `base_ref` and `request_id`, never the ids; of its labels only `via:<id>`. **Never** trust identity from a payload field: map external users to
members only through a verified link (`external_identities`) or a rule approved in review.

**Connections** are per team: two teams may connect the same external workspace, each with
its own secrets and webhook URL (whether the provider allows a second install is up to
the provider). A provider that delivers a workspace's events to one install only (Slack) declares
`workspaceUnique: true`: then a second live connection for the same `external_id` in **any** team is
refused with the very same `CONFLICT` as within a team (it never names the other team) and nothing is
written; a revoked one doesn't count. OAuth `state` is bound to the browser that consents: the callback refuses
unless the bind cookie set by `POST …/start` comes back: `__Host-board_int_<provider>` (`Path=/`,
`Secure`) on an https hub, `board_int_<provider>` (`Path=/integrations/`) on an http dev/local hub.
Inside the desktop shell only, the web passes the bind in the connect window's name and the app
sets the cookie in its connect window; a browser tab gets `_blank` and uses the cookie it has (D42).

**Reconnect.** A second live connection for the same `(team, provider, external_id)` is refused with `CONFLICT` (`this <name> is already connected`) and leaves nothing behind: no connection row, no sealed secret, no journal row; the live one is untouched. The callback page shows that message. If your provider creates a new external resource before `exchange` returns (GitHub's App-manifest flow makes a new App each time), return a **stable per-resource id** as `external_id` (the App id, not the account), so a reconnect that made a new resource is a new connection rather than a clash with, or a silent takeover of, the old one; the admin revokes the old connection when it is no longer wanted.

**Connect flows.** `authorizeUrl` is a GET redirect. A provider that wants a POSTed form (GitHub's
App-manifest flow) declares `connect.manifestForm({state, redirectUri, webhookUrl, provider, config}) → {action, fields}`
and `connect.formHost` (one of `hosts`) instead: `/start` then returns `{form, bind}` and refuses a form whose
`action` isn't https on exactly `formHost` or whose fields aren't strings; the web renders a real POST form the
admin submits; the web CSP's `form-action` names each `formHost`. Every flow gets `webhookUrl` (the connection's
id is minted at `/start`, so a manifest can name its webhook URL), and for a reconnect, from your team's newest
active connection of this provider (else `{}` each), `provider` (its `settings.provider`; for a connection made
before 026, its `config`, where those values were kept then) and, apart, `config` (its `settings.config`, an
admin's, limited to your `configKeys` when you declare them). **Never copy `config` into the `settings` you
return**: that would turn an admin's input into a provider fact that can never change; build them from what the
provider says and from `provider`.
`exchange` may return `settings` (non-secret scalars ≤ 2 KB → `settings.provider`, see below; `autonomy` is
ignored) and `next_url` (https on one of `hosts`:
the success page's single "Continue on <name>" link, e.g. installing the app). Anything else it returns, such
as an id or org, is ignored.

**Pending connections (D97).** A provider whose app must be created first (Slack, from a configuration
token) declares `connect.prepareInputs: [...]` and `connect.prepare({input, webhookUrl, redirectUri,
identityRedirectUri, provider, config, fetch})`. The admin's `POST /api/integrations/<id>/prepare {input}` reaches it with
only the declared keys (strings of 1–4096 bytes). The input lives only in that call: **never** put it in an error
message, a log line, `secrets` or `settings`; the registry turns any throw into a fixed `VALIDATION` and logs a code
only, and the `fetch` you get (declared `hosts`, 10 s, no retries) throws fixed text with no `cause`. Answer either
`{needs:{fields, create_url}}` (the admin creates the app at `create_url`, https on `hosts`, and pastes `fields`;
the second `POST /api/integrations/<pending id>/prepare` calls you again with them, and must not answer `needs`) or
`{secrets, settings?, match, external_id?}`. The secrets are sealed on a pending row under the id the connection
will keep; `webhookUrl` already names it, and `identityRedirectUri` is the exact identity callback (put both
redirect URIs in your manifest). The row lives one hour, claims no workspace and receives no webhooks (a pending id
is the unknown-connection 404), with one exception: declare `connect.handshake({payload, headers}) → boolean`
(needs `ackBody`; Slack: `payload.type === 'url_verification'`) and a delivery to a ready pending id whose
`verify()` passes under that row's own secrets, whose `parseBody` succeeds and for which `handshake` returns exactly
`true` is answered 200 `text/plain` with `ackBody`'s string (1–256 printable ASCII characters, the challenge;
anything else is the 404). Nothing else runs for it: no handler, lease, rate token, audit, journal or promotion. `authorizeUrl` and `exchange` then get `provider` overlaid with your pending
`settings`, and `exchange` gets the pending `secrets` (the app's client secret: throw fixed text only, never the
provider's answer or your arguments, and don't count on the log's redaction); it must return `match` with exactly the same keys and values
(Slack: `app_id` from the `oauth.v2.access` answer and `client_id`), and the recorded `external_id` if you gave one,
else the app is refused and the row stays. It may add secret kinds (the bot token), never replace a pending one.
Promotion keeps the id and copies the sealed secrets unchanged; `settings.pinned` = `match`, fixed for good, and
`settings.provider` = exchange settings ⊕ pending settings ⊕ every `match` key ⊕ the registry's `hub_url` (so
don't use `hub_url` as a `match` key: that answer is refused). The
hub never deletes the app it made at the provider: the admin is told to. Such a connector has no plain
`/start` flow (404); only the pending row's callback connects it.

**Identity links (D98).** A `workspaceUnique` connector may declare `identity: {issuer, jwksUrl, workspaceClaim,
subjectRe, authorizeUrl({state, nonce, redirectUri, connection, secrets, fetch}), exchange({query, state,
redirectUri, connection, secrets, fetch}) → {id_token}}` (OpenID Connect, scope `openid` only). A member starts it
from the hub (`POST /api/integrations/<id>/identity/start`); you build the authorize URL (https on `hosts`) and
trade the code for the raw `id_token`; the registry verifies it (RS256 against `jwksUrl`, `iss`, `aud` = the
pinned `client_id`, `exp`/`iat`, the nonce, `workspaceClaim` = the connection's `external_id`, `sub` ~
`subjectRe`) and writes the link. `connection` is `{external_id, settings: {pinned, provider}}` (frozen; no
`config`, which admins edit): take the client id from `settings.pinned`. Throw fixed text only: `secrets` holds your app's client secret. Then, inside
`ctx.act(action, {subject}, run)`, `s.actAs(m)` takes only `ctx.memberFor(subject)` (a linked member who can
write): resolve the actor with it and do nothing for `null` (reply with the hub URL so they can link). Use
`ctx.subjectFor(memberId)` to reach a member (a viewer too) in a DM. Never link from the provider side or from
an email match.

**Settings namespaces, admin config and links (D42 addendum C1).** A connection's `settings` holds `autonomy` and
`config` (an admin's: `PATCH /api/integrations/:id` merges them key by key, `null` deletes a key, a `config` key
that `provider` holds is refused, the merged `config` ≤ 8 KB) and `provider` and `pinned` (written once, with the
row; migration 026's trigger aborts any later change, including adding `provider` to an old row). `provider` is
what your `exchange` (or `verifyToken`, or a pending `prepare`) returned as `settings`, plus every `match` key and
the registry's `hub_url`. Read workspace, app and client ids **only** from `ctx.connection.settings.provider`,
`settings.pinned` or `ctx.connection.external_id`, never from `config`, and bind security checks (which workspace
a payload must come from) to `external_id`. A connection made before 026 has no `provider`: if you need a
provider fact, refuse to act when `provider` is missing or its team id is not `external_id` (fail closed; the
admin reconnects). Declare `configKeys: ['default_board_id', …]` to limit what an admin may set (an undeclared key
with a value is `VALIDATION`, `null` for it a no-op); without it any key name of 1–64 `[A-Za-z0-9_-]` starting
with a letter is accepted. **Links to the hub** come only from `ctx.hubUrl` (the hub's `BOARD_PUBLIC_URL`
origin, read at boot; `null` when the hub has none or it is not an https origin, and then you send no link):
never from `config`, `provider.hub_url` or anything in a payload.

**Planned interface (not built yet; do not rely on it).** Two spec fields are specified in CONTRACT but
not yet checked or honoured by `defineConnector` or the registry. `showsWebhookUrl: true` (Sentry slice S-A,
D42 addendum "the Sentry connector"): for a `token` connector that takes webhooks, owners/admins get the
connection's `webhook_url` in `GET /api/integrations` and in the token connect answer (members never do), so
the admin can paste it into the provider after connecting; the URL is built from the connection id, which
members already see, so it is not a secret and `verify()` stays the only gate. `signals: ['incident']`
(S-C3, D99): inside `act()`, `s.signal(kind, {card_id})` for a card **this connection created** writes one
journal row `integration.signal` `{connection_id, kind, card_id}` (ids only, never text), at most one per
card and 6 a day per connection; it moves no card, dispatches nothing and notifies nobody by itself, and a
consumer must re-read the card on the hub before acting. S-A also adds the rate rule
`integration_card_day_conn` (100 new cards a day per connection, every connector).
