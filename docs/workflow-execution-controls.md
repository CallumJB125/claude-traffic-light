# Human workflow execution controls

Execution/control previews are immutable and inert. The separate human Start, Resume, Retry, Pause and Cancel routes use their captured current authority; no preview dispatches work, creates a run, answers a permission, edits a task or transfers code. These server routes are not execution tools in the desktop or remote MCP catalog, SDK, or imported recipes. Human UI and actual runner acceptance remain separate gates.

After creating a current039 plan, its human issuer may POST `/api/workflow-plans/:plan_id/execution-preview` with `request_id`, exact `plan_hash`, `purpose:"start"` and `declared_paths`. The array matches every fixed step position, with at most16 unique normalized relative paths per step and200 characters per path. Literal paths and terminal `/**` prefixes are advisory declarations. Empty arrays are allowed for sequential work. Requested concurrency2 remains2 and reports missing/overlapping/unknown parallel scope explicitly. No filesystem lock or knowledge of undeclared edits is implied.

GET `/api/workflow-execution-previews/:execution_preview_id` returns a fresh scoped staff/viewer projection and the exact source, execution-preview and path hashes. Initial validity is at most24 hours and no later than the source plan's expiry; replays retain IDs/hashes/expiry. Boot, rollback, account/credential/member replacement and stale source require a fresh review. If operator-configured GitHub verification is available, a fixed read-only lookup outside the board queue resolves each server-captured base reference to a complete commit identity. The complete lookup set is bounded to10 seconds and at most8 selected tasks; lookup failure remains `BASE_REVIEW_REQUIRED`. Source, principal, repository and execution observations are checked again before persistence and delivery. Human review is still required. There is no automatic merge or source transfer.

POST `/api/workflow-plans/:plan_id/start` accepts exactly `request_id,plan_hash,execution_preview_id,execution_preview_hash,path_intent_hash,expected_revision:0,confirm:true`. All three reviewed hashes and the preview's actual human credential must match. Parsing grants no authority. Effects, fixed attempts, retained owned markers, bounded result and durable receipt commit together. Repeating a request rechecks current scope and returns a current projection without another paid action. Changing that request's payload is refused. The legacy037/039 schema and hashes remain unchanged; ordinary lifecycle versions are recorded in separate progress bindings.

POST `/api/workflow-executions/:execution_id/preview` accepts the closed `resume` or `retry` purpose, source plan/hash, exact execution revision and declared paths. Retry also names the exact failed/uncertain `previous_attempt_id` and position. A fresh preview captures current source and base identities without amending the frozen original plan; it lasts at most24 hours. A preview from an earlier boot, expired authority or changed revision cannot revive a launch. After review, POST the matching hashes and `confirm:true` to `/api/workflow-executions/:execution_id/resume` or `/api/workflow-executions/:execution_id/steps/:position/retry`. Resume does not silently retry a failed or uncertain paid attempt. Each step has a hard8-attempt bound. Fixed provider, target, budget, dependencies and concurrency1 or2 remain unchanged; there is no fallback or implicit downgrade from2 to1.

POST `/api/workflow-executions/:execution_id/pause` and `/cancel` accept only `request_id,expected_revision`. The current issuer or an owner/admin may pause scheduling. An already claimed run remains observed. Cancel additionally uses the existing involved-actor stop/cancel policy for the exact attempt; the response reports stop requested with `confirmed:false`, not external process completion. GET `/api/workflow-executions/:execution_id` returns bounded current selected-board staff/viewer status and excludes task briefs, credential references and private proof bytes. All inputs, snapshots and result projections are capped at32 KiB, with at most128 durable control receipts per execution.

Automatic preparation failure, claimed timeout, parked answers, releases and handoff follow-ups never choose a new paid request UUID. Their cleanup remains observed; another paid attempt needs explicit human Retry. An observed complete result binds the exact run/fence, repository and selected evidence before the ordinary active-run pointer is cleared. A successor needs the exact completed predecessor plus either actual captured current human review or a fresh hub-verified PR with exact branch, same repository identities, reviewed base reference, captured40-character head SHA and complete merge SHA. Old runs, manual Done, prefix branches, retargeted bases, forks, changed evidence and missing metadata cannot release a successor. Claim and token replay check current reviewer authority too. The successor keeps its own reviewed base commit; merge evidence does not move code automatically.

Reserved Codex plan approval remains a separate actual human permission answer bound to the exact run and declared paths. Changed declarations invalidate that private proof without resetting, answering or retrying the old permission. Pause/reboot does not fabricate a new answer or execution.

Migration044 retains private immutable snapshots, authorization/progress/receipts/proofs and durable owned-intent fencing. Additive045 supplies keyed source/state bindings and exact verified PR metadata while preserving applied037/039/044 bytes. Erasing private parents disables the retained request marker before deleting history and cancels only its matching still-pending dispatch. Claimed runs/cards/journal are not changed into fabricated stops. The narrative-free marker cannot be deleted or revived into an ordinary request. Boot pauses scheduling and invalidates unclaimed intents; it never resumes paid work. Path declarations remain advisory in the selected board/repository scope: platform aliases, case and undeclared edits can remain unknown, and no global non-overlap or filesystem lock is claimed.
