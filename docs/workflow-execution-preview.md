# Workflow execution preview

Checkpoint1 provides an inert plan preview for a current signed-in team account. It does not provide Start, Pause, Cancel, Resume, Retry or execution tools. Creating a preview does not dispatch a task, create a run, edit a card or recipe, answer a permission request, merge or deploy.

Use an existing immutable workflow instance of1–8 cards. Explicitly assign every card to the same linked repository through ordinary card edits. `POST /api/workflow-instances/:instance_id/preview` takes the closed schema in `board/shared/workflow-execution.js`: UUID request ID, exact board/repository, immutable recipe version/hash, explicit concurrency1 or2 and each step's position/card/version/fence/provider/target member/budget/plan-review choice. Optional dependency pairs are same-instance positions and must form an acyclic graph with at most28 edges; omitted pairs mean sequential order. Codex requires an explicit no-budget choice because it has no native monetary cap. Current teammate/admin budget restrictions remain.

The hub saves a bounded immutable snapshot and source hashes, with server-only captured issuer/credential references. It stores no bearer token, private chat, local environment or logs. Exact request retries return the same plan identity/hash/expiry after current authority and source checks; changed choices conflict. A failed final response check can withhold a preview already saved, so retry explicitly with the same request ID rather than assume metadata rolled back. Team quota is1000 saved previews and response/snapshot limit is32KiB.

`GET /api/workflow-plans/:plan_id` lets current staff/viewers read a fresh projection of that plan. An optional repeated `board_id` query can narrow current board access; it cannot widen team access. Credential/member ownership, issuer/target identity, current card version/fence/content/plan policy and repository linkage are rechecked in the board queue and synchronously at final delivery. Credential references and private source hashes are absent from responses.

Runner readiness is a current report from an accepted enrolled connection, not permission or completion. Unknown sign-in/readiness is blocked. The preview always says `grants_execution:false`, `execution_enabled:false`, `authorization:null` and `requires_fresh_human_start:true`. Its validity is at most24h; expiry never refreshes on retry. A different hub epoch reports paused after reboot, and a detected backward clock pauses previews until the hub clock/process is corrected. No old preview restores execution authority.

Future Start needs separate source, owned-intent claim/requeue/boot and exact predecessor-review guards plus actual human UI/Codex acceptance. Advisory overlap declarations cannot guarantee all edits are known. Task Done, model messages, receipts, reports and plan hashes do not release dependencies or approve a model action. Downstream unreviewed merge/rebase/base changes require a fresh explicit plan.
